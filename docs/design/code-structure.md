# Code structure and testing

Answers [How is the code split into modules and tested?](https://github.com/Shtian/bff-wow/issues/9). Builds on the sync resolution in #8 and `docs/adr/0001-owner-written-records-gossiped-by-server-time.md`. Domain vocabulary from `CONTEXT.md`; architecture vocabulary (module, interface, seam, adapter, depth) as in the `codebase-design` skill.

## The idea in one line

Almost all behaviour lives in one deep, pure-Lua module, **Core**, behind a small interface. The WoW-facing code is thin. Offline tests and `/bff sim` drive real Cores against each other through a fake link.

## Modules

| Module | Pure? | Owns |
|---|---|---|
| **Core** (`Core/`) | yes | Everything BFF knows and decides: Member records, sync, Feed, panel rows, saved-data layout. Details below. |
| **Snapshot** (`Game/Snapshot.lua`) | no | Reads the name (first, and the last name as UnitName's second value on Forever), level, XP, zone, class, gold, professions (through `Professions.read`) and GUID, counts deaths (kept per Character in `BFF_CharacterDB`), and calls `core:updateOwn(character)`. `Snapshot.locate()` reads where the Character stands, for Core's `locate`. `Snapshot.encounter(...)` turns `ENCOUNTER_END`'s payload into `encounterEnded()`'s, with the instance type and the group, secret values as nil. `Snapshot.catch()` reads the loot window through `Catches.read` on `LOOT_READY`, for `caught()`. `Snapshot.doing()` reads what the Character is doing right now, for `doing()`: in combat, at a vendor or the auction house (kept from `MERCHANT_SHOW`/`MERCHANT_CLOSED` and `AUCTION_HOUSE_SHOW`/`AUCTION_HOUSE_CLOSED`), resting and flying, a secret value as false. It also calls `core:questHandedIn()` on `QUEST_TURNED_IN`. |
| **Bags** (`Game/Bags.lua`) | no | Offers a bag item as a Spare: the item on the cursor (the Spares tab's drop slot) or the first bag item matching a link (`/bff spares add`). Passes its item GUID and binding to `core:postSpare`, which refuses an item that can't be traded. Also tells Core where a posted item is now (`findItem`), for `core:bagsUpdated` on `BAG_UPDATE_DELAYED`. |
| **Channel link** (`Game/ChannelLink.lua`) | no | The production link adapter: joins and hides the Crew channel (including filtering its system notices out of chat), reads the member list, the join and leave notices and the "No player named …" and "Player is offline." notices and tells Presence (below), sends each message as addon whispers to the peers Presence names, in the chunks Framing (below) splits it into, and decides when the link is up or down. It keeps what needs the game: joining and leaving, lockdown, checking that event arguments are readable (a secret value never reaches Presence), `Ambiguate`, the notice patterns, the player's own first and last name, ChatThrottleLib, AceComm's receiving side (it registers the prefix and puts an older BFF's multipart messages together) and the outbox: what is still to send per peer (see "Framing" under the link port). It holds no list of peers. Its half of the sync trace (`setTrace(fn)`): each message sent per Character with its bytes and chunks, each whisper received with its sender and bytes, a message of several chunks being whole, a message lost, each chunk's result (a failed one with the game's result code), unsent chunks dropped and why, the link going up or down and why, chat restriction changes, "No player named …" notices (one that names no peer with the peer keys it was compared with), "Player is offline." notices, a system message the game won't let it read within 5 s of a whisper (with the instance type and lockdown, never the text), entering and leaving an instance, leaving the group or it disbanding, the peers list changing and why, a peer going silent, being tried again and being heard again, and stranger whispers held or dropped. `state()` gives `{ up, reason, peers, instance, lockdown }` for `/bff report`. On Forever addon messages sent to a custom channel never arrive, so the channel only carries presence. See `docs/research/channel-spike.md`. |
| **Presence** (`Link/Presence.lua`) | yes | Who is in the Crew channel and can be whispered: the peers, held strangers, whether the first member list is in, and whether a chat notice is about one of ours. Decodes no messages and knows nothing about Members. See "Presence" under the link port. Tested through its own interface (`presence_spec`). |
| **Framing** (`Link/Framing.lua`) | yes | Splits a message into chunks of at most 255 bytes and puts the chunks received back together, per sender and message id, in any order. Reports a message that stays incomplete as lost. Knows nothing about what a message holds. See "Framing" under the link port and ADR 0007. Tested through its own interface (`framing_spec`). |
| **Sync log** (`Game/SyncLog.lua`) | no | The sync trace's last 300 lines, kept whether or not they are printed: a ring buffer, oldest dropped first. App saves it per Character in `BFF_CharacterDB.syncLog` on `PLAYER_LOGOUT` (logout and reload) and restores it at start, followed by a separator with the date this session began. Tested offline (`sync_log_spec`). |
| **UI** (`UI/Skin.lua`, `UI/CampSheet.lua`, `UI/CampScene.lua`, `UI/Panel.lua`, `UI/PocketCamp.lua`, `UI/TipDialog.lua`, `UI/TogetherTab.lua`, `UI/CatchesTab.lua`, `UI/GoalsTab.lua`, `UI/Minimap.lua`, `UI/MapPins.lua`, `UI/Away.lua`, `UI/ToastQueue.lua`, `UI/Toasts.lua`, `UI/Settings.lua`, `UI/Report.lua`, `UI/Contact.lua`) | no | Renders Core's rows and summaries and sends user commands to Core. Shows no state it worked out itself. Skin is the shared flat look (colours, fonts, window, buttons, Feed icons) for the panel, the popup, toasts and map pins. CampScene draws Core's `camp()` as pixel art from the sheet CampSheet describes (generated by `scripts/camp-art.mjs`), for the panel's band, the popup and the small figures on Roster rows and toasts (`docs/design/camp.md`). PocketCamp is the small on-screen Camp: it draws Core's `pocketCamp()` with a CampScene band of its own, Panel shows Core's `tip()` as a card under the band, and TipDialog shows it once as a window (`docs/design/pocket-camp.md`). ToastQueue is pure and tested offline (`docs/design/toasts.md`). Contact is the Get in touch window, from the header's message button: the GitHub issues and CurseForge links in boxes selected for Ctrl+C, and a button to the Report. |
| **App** (`BFF.lua`) | no | Wiring only: creates Core, routes WoW events (`UI_SCALE_CHANGED` and `DISPLAY_SIZE_CHANGED` redraw the panel and the Pocket Camp, for the Camp's art pixel), runs a 1 s `C_Timer` ticker that calls `core:doing(Snapshot.doing())` and `core:tick()`, and handles slash commands. The sync trace is always on: one `trace(line)` function, given to Core and the channel link at start, stamps each line with the time of day and `GetTime()` and keeps it in the sync log. `/bff debug sync` turns printing the lines on or off for the session. In a dev checkout, once the `/bffdev` console has been opened, printed lines go to the console's log instead of chat (`ns.traceSink`), and its **Sync trace** box turns printing on or off too. `/bff report` opens the Report window. |

The first draft's Zones module is dropped from v1, because only the overlap finder needed it. The overlap finder (the Together tab) works from levels and a dungeon table instead.

## Core

### Interface

Core is created with:

- `db`: the whole `BFF_DB` table. Core owns its layout, defaults and migrations, settings included.
- `now()` and `random()`: the clock (`GetServerTime` in game) and randomness, so tests are deterministic.
- `link`: the outgoing half of the link port (`send(string, to)`).
- `listener`: receives Core's events.
- `initialLogin`: `isInitialLogin` from `PLAYER_ENTERING_WORLD`, so Core can tell a login from a reload (see `docs/design/feed.md`).
- `maxLevel`: from `GetMaxLevelForPlayerExpansion()`, for max level Feed entries.
- `utcOffset`: how many seconds local time is ahead of server time, so `feed()` starts each day at local midnight and `playTimes()` shows local hours (default 0).
- `locate()` (optional): where the Character being played stands, as `Snapshot.locate()` reads it: `{ mapId, x, y }` in the open world, `{ instance }` inside an instance, or nil when it can't be read. Core calls it just before its own DATA goes out (a zone change, a ding, the heartbeat), and every 2 s for Where (below), so moving never changes the record or sends DATA; it sends a small WHERE instead. The Ledger rounds the position to 0.1%, keeps the last open-world spot read (or the record's) inside an instance, and keeps the last known spot on nil.
- `itemLink(itemString)` (optional): the game's link for an item string, as `Snapshot.itemLink` reads it, or nil while the item isn't cached. Spare texts say "an item" until then (`docs/design/spares.md`).
- `itemLook(itemId)` (optional): how the game shows an item, as `Skin.itemLook` reads it: `{ text, icon, edge }`, the name in its quality colour, the icon and the quality colour, each nil while it isn't cached. Rare finds use the English name until then (`docs/design/feed.md`).
- `findItem(itemGuid)` (optional): where a posted item is now, as `Bags.findItem` reads it: whether it's in the bags or bank (nil if the game can't say), and whether it's equipped.
- `finalBosses` (optional): encounter ID to instance name, the kills that are Clears. Defaults to `Core.FINAL_BOSSES`, from the dungeon table's `finals`; tests and the dev sim pass their own while Forever's IDs aren't known.
- `gossip` (optional): the Gossip module to use. Only FakeNet passes one, for a client that syncs like an older BFF (`tests/fixtures/legacy_gossip.lua`).

Inputs:

- `updateOwn(character)`: the current state of the Character being played, from Snapshot.
- `tick()`: once a second. Core decides what is due (reply delays, debounced sends, heartbeat, online timeouts, pruning), and counts the second towards Play times.
- `received(string)`, `up()`, `down()`, `gone(name)` and `sendFailed(name)`: the incoming half of the link port.
- `bagsUpdated()`: on each `BAG_UPDATE_DELAYED`, never before the first of a session. Core checks where each own Spare's item is (ADR 0004).
- `caught(loot)`: on `LOOT_READY` (a loot window's catch once), from `Snapshot.catch`: `{ items, zone, subzone, mapId }`, or nil when the loot isn't from fishing. Each item goes into the own record as a Catch, shared with the next send, or now for a rare find, which makes a Feed entry. Types caught can reach a Crew goal step (`docs/design/catches.md`).
- `doing(facts)`: every second, from `Snapshot.doing`: `{ combat, vendor, auction, resting, flying }`, each true or not. Core picks the one to show (flying, the auction house, a vendor, fighting, which lasts 20 s past the end of combat, then resting), shows it on your figure in the Pocket Camp and tells the Crew with a DOING when it changes (Doing, below). The record doesn't change.
- `questHandedIn()`: on `QUEST_TURNED_IN`. The Pocket Camp plays the quest animation on your figure, and the next DOING tells the Crew, if it goes out within 90 s.
- `encounterEnded(encounter)`: on `ENCOUNTER_END`, from `Snapshot.encounter`: `{ encounterId, success, instanceType, party }`. A known final boss killed in a party or raid instance, in a Crew, is a Clear in the own record (ADR 0005); returns the instance's name, or nil and why not (`docs/design/trophies.md`).
- Commands: start, join and leave a Crew, change the display name, Set as Main, Remove and re-add a Member, Pause sharing, and settings (see `docs/design/joining-a-crew.md`). Spares: post (with the item's GUID, kept locally, and its binding: an item that can't be traded is refused), withdraw and Give one, and make and withdraw a Claim (`docs/design/spares.md`).

Outputs:

- `link.send(string)`: best-effort (see the link port below).
- Listener events:
  - `changed`: re-read whatever you show (`rows()`, `feed()` and the rest). Also fires when a Member passes the 12-minute online timeout, even though no record changed. Settings don't fire it.
  - `settingChanged(key, value)`: a setting really changed (setting a value it already has fires nothing). App passes it to Panel, Minimap, Toasts, Settings and MapPins, and each ignores keys it doesn't use: Toasts clears its queue when `toasts` turns off, Minimap shows or hides the button on `minimap`, Panel redraws on `paused` (its footer status), `camp` and `pocketCamp` (its Tip), and moves, resizes and redraws on `panelPlace`, PocketCamp redraws on `camp` and every `pocketCamp*` key, the Settings page updates that key's control, and MapPins redraws on `mapPins`, `mapPinSize` and `camp`.
  - `feedEntry(entry, outlets)`: a Live event from the Feed. While the Camp is on, an entry about a Member the Roster shows has `figure`, that Member's shown class, for the toast. Core decides where it goes: `outlets` is `{ chat, toast }`, from the chat-line and toast settings, and App prints `entry.text` and shows a toast exactly as told, reading neither setting. With both off it isn't fired, and the entry stays unseen for While you were away.
  - `pocketCampAnimation(animation)`: a new Feed entry the Pocket Camp animates, made while running: `{ kind, memberId }`, kind "ding", "maxLevel", "death" or "rareFind" for a Member by its fire, or "goal" (no `memberId`) for the fire; also "quest", for a Member who handed in a quest (from a DOING, or your own). Fired only while the Pocket Camp shows, whatever the chat-line and toast settings are, and it marks nothing seen (`docs/design/pocket-camp.md`).
  - `tip(tip)`: a Tip is offered for the first time, as `tip()` gives it. Fired once per Tip on the account; App shows it as a window once out of combat.
  - `reaction(news, outlets)`: a live Reaction to one of your entries, fired and shown the same way as `feedEntry`. Toasts for the same entry merge (see `docs/design/reactions.md`).
  - `spare(news, outlets)`: a live Spare notice (a Claim now winning yours, or one Given to you), fired and shown the same way as `feedEntry` (see `docs/design/spares.md`).
  - `spareGone(gone)`: at the first bag check after a real login, a Spare whose item is gone was withdrawn (`action` "withdrawn": App says so in chat) or has a Claim (`action` "ask", with its `winner`: App asks whether to Give or withdraw it).
  - `awaySummary(summary)`: While you were away has settled after an initial login. Fired only when the popup setting is on and it isn't empty. App shows it once out of combat. It comes worded, so the popup only lays it out: the scoreboard's `intro` ("2 things happened while you were away."), the `maxLevel` its level bars run to, each Character's `label` ("Alt Jaina", the Main's name, or nil for a Main named like the Member) and `gained` ("+2" or "new"), each Member's `tags` (`{ text, highlight }` for joined and left), a `highlight` flag on each profession line, and `catches`: the line of new types others caught, then the rare finds missed. With the Camp on, `camp` is the Camp at `Core.CAMP_LAYOUT.awayColumns` without the tent, each actor with `gained` (its Main's, as the scoreboard words it; nil with nothing gained) and `highlight` (max level), and `intro` reads "The fire kept burning. 7 things happened in camp."
  - `moved`: a Member's live spot changed (a WHERE). App redraws only the map pins, and only while the map is open (it redraws on opening).
  - `notice(kind)`: one-off messages ("BFF is out of date", "you left the Crew").
  - `crewChanged`: the Crew was joined or left. App tells the channel link to join or leave the channel from `crew()`.
- Settings: Core holds one ordered list of the local settings (`docs/design/settings-and-release.md`). `setting(key)` reads one and `setSetting(key, value)` sets it; `settings()` is the Settings page's ready-to-render read, a section per `{ title, settings }`, each setting `{ key, kind, label, value }`, plus `choices` (`{ key, label }`) for a `choice` and `needs` (the on/off setting it's greyed out without). The named methods (`isPaused()`/`setPaused()`, `isMinimapShown()`/`setMinimapShown()`, `isChatLinesOn()`/`setChatLines()`, `isAwayPopupOn()`/`setAwayPopup()`, `isToastsOn()`/`setToasts()`, `toastSound()`/`setToastSound()` and `toastPosition()`/`setToastPosition()`) are one-line wrappers over these. `setPanelPlace(width, height, left, top)` and `resetPanelPlace()` save the panel's size and position (clamped to its limits, `Core.PANEL_MIN_*`/`PANEL_MAX_*`), and `panelPlace(screenWidth, screenHeight)` says where it opens on this screen: shrunk to fit, moved onto it, and with nil `left`/`top` for centred. `minimapIcon()` is the saved table LibDBIcon keeps the button's position and the minimap setting's hidden flag in. `setPocketCampPosition(x, y)` saves where the Pocket Camp was dragged to.
- Tips: `tip()` is the first unanswered Tip ready to render (`{ key, title, text, accept, dismiss }`), or nil; `acceptTip(key)` answers it and turns its feature on, `dismissTip(key)` only answers it. Both fire `changed` (`docs/design/pocket-camp.md`).
- Reads: `crew()` (code, channel name and password, a `leaving` flag while a leave is pending, `alone` while no other Member is known, and `status`: the Roster footer's finished line, the first that applies of leaving, appearing offline and waiting for your Crew, else nil; or nil outside a Crew) and `displayName()`.
- Ready-to-render reads for UI: `rows()` (each row and Character with its finished `lastSeenText`: "5m ago", "online" on a row while online, nil on your own row; each row's `status`, the right-hand text, "by the fire" and "asleep · 5m ago" with the Camp on, else its `lastSeenText`; and each other Member's `section`, "BY THE FIRE" or "ASLEEP IN CAMP" sorted Online first with the Camp on, else "CREW"), `summary()` (the counts, Spares for you, and `header`: "1 of 4 online", or "2 of 5 by the fire" with the Camp on), `camp(columns)` (the Camp at a band `columns` art pixels wide, in `Core.CAMP_LAYOUT`'s geometry, or nil while the `camp` setting is off: actors, graves, tent and more, `docs/design/camp.md`), `pocketCamp()` (the Pocket Camp: the fire and the online Members, each seated, adventuring or fishing, with how it's shown, or nil while it or the Camp is off, `docs/design/pocket-camp.md`), `feed()` (the Feed tab's entries grouped by day, each day with its finished `title` ("TODAY", "YESTERDAY", "MONDAY 02 NOVEMBER"), each entry with `highlight` (the news), `new` (see the Feed visit below) and its reactors in order, yours named "You" and marked `you`, plus the unseen count), `goals()` (the Goals tab's row per Crew goal track, `docs/design/goals.md`), `trophies()` (every Crew goal rung reached and every instance the Crew has cleared as a trophy, for the Goals tab's latest win, shelf and cabinet, each with its finished `date`, `quality` and `fresh`, a clear's with its `party` by name; the cabinet's `dungeons` and `raids` grids, a slot per instance; `openGoals()` and `leaveGoals()` make the Goals visit its since-last-opened count holds through), `playTimes(memberId?)` (the When tab's grid for the Crew or one Member, with its finished `title`, `intro` and `note`, `docs/design/play-times.md`), `mapPins()` (a world map pin per other Member the Roster shows, at their shown Character's last-seen spot, the live one from a WHERE when it's newer than the record; `figure`, the shown class for the Camp's seated figure, while the Camp is on; `size`, the `mapPinSize` setting; none while the `mapPins` setting is off), `spares()` (the Spares tab's rows, From the Crew and Yours, each with its finished `info` line, its buttons (`primary` Claim or Give with `enabled`, `secondary` Withdraw, nil when not shown) and `highlight` and `dimmed` flags, plus `claimFor`: your Characters for the Claim menu, Main first, `{ guid, label }`), `professions(order?, sortBy?)` (the Professions tab's grid: a row per Member and a cell per profession, their best Character's skill, `docs/design/professions.md`), `catches()` (the Crew's Catches: per type, the earliest catch across the Crew and the Crew's count, the types caught out of those counted, and the unlisted catches, `docs/design/catches.md`), `catchesTab(group?, show?)` (the Catches tab: that as a field guide, grouped by where to fish or type and filtered by Show, every tile, tooltip and empty state worded, and the Group and Show menus, `docs/design/catches.md`), `together(measure?, selected?)` (the Together tab: friends and every dungeon shown placed on the level line in `Core.TOGETHER_LAYOUT`'s geometry, what's shared with the Members picked, and the Show menu, whose choices are the `together*` settings, `docs/design/together.md`; the dungeon table is `Core.DUNGEONS`, and `Core.selectTogether(selected, memberIds, add)` gives the pick after a click), `spareItems()` (the item GUIDs of the open Spares the Character being played posted), and `unseen()` (the unseen count alone, for the minimap tooltip and the panel's sidebar while the Feed isn't shown). UI never sees a Member record.
- The Feed visit: `openFeed()` is called on every draw of the Feed tab, before `feed()` is read. It starts a visit if none is open, and every entry (or Reaction to your own) unseen at that moment is seen, and **New** in `feed()` until `leaveFeed()`, called on leaving the tab or hiding the panel. Core marks entries seen itself when it fires `feedEntry` (or `reaction`, `spare`) or `awaySummary`, so an entry a Live event already showed is never New.
- `react(key)` reacts to someone else's Feed entry, with a key from `feed()` or the summary.
- The sync trace: `setTrace(fn)` makes Core call `fn(line)` with a line of text (no timestamp) for each message it sends (type, each record's name, id and version or a DIGEST's count and versions, and its size in bytes; a WHERE's size alone) and receives (sender, type, the decode result `ok`, `invalid` or `newer`, a WHERE's `ok` or `ignored`, a DIGEST's versions, and per DATA record whether it was merged and how late it is: now minus its version). `setTrace(nil)` turns it off; Core then builds no lines. Off for every new Core. Tested in `trace_spec`.

### Inside Core

These are internal seams: separate files for locality, tested only through Core's interface, with nothing swappable behind them. The one exception is the `gossip` dep, so mixed-version tests can run a client with an older BFF's Gossip.

- **Ledger** (`Core/Ledger.lua`): what we know. Holds the own record and copies of everyone else's, the merge rule (a higher version wins), the Remove list, the "left" flag, last-heard times, and 180-day pruning. It stores and writes records (versions, the bump, what Gossip sends) and prunes on every own write, but never reads the Spares layout: the Spares module writes its part of the own record through `changeOwn`, and prunes it through the pruner it hands over with `pruneWith` at setup, since only Spares knows which Spares and Claims have ended. Removing a Member deletes their record and drops future copies, but keeps the last version seen: a refused copy that is newer raises it. The DIGEST lists removed Members with that version, in turn with the held records, so no peer owes them to you (one removed before versions were kept is listed with 0 and sent once more). Re-adding takes them off the list and forgets the version, then sends a DIGEST, and peers reply with DATA.
- **Gossip** (`Core/Gossip.lua`): when to talk. Owns the DIGEST and DATA rules, 1–4 s reply delays and suppression, send timing (immediate, 10 s zone debounce, "later" changes such as XP within 60 s, 5-minute heartbeat), the DIGESTs that recover lost messages (see Sync below), the "record changed" and "reply owed" flags, and Pause.
- **Feed** (`Core/Feed.lua`): turns a before/after record pair from Ledger into Feed entries, including skipped versions such as 22 → 24. For others' "gave" entries it asks Spares (`Spares.newlyGiven`) what was newly Given between the two; your own come from Spares when you Give. Feed owns how a "gave" entry looks. Also owns the capped log, seen flags, and when While you were away is ready. See `docs/design/feed.md`.
- **Reactions** (`Core/Reactions.lua`): the pure parts of Reactions: which Reaction each entry kind has, the key a Reaction points at an entry by, how keys are stored in a record and pruned, and the wording the owner sees. Feed attaches Reactions to its entries. See `docs/design/reactions.md`.
- **Spares** (`Core/Spares.lua`, with `Core/SpareRules.lua`): the whole Spare lifecycle, and the only Spare interface Core uses. Owns posting, withdrawing and Giving, making and withdrawing Claims, expiry, who wins (ADR 0003), the item-gone state and bag check (ADR 0004), the item GUIDs of own Spares (local only), the Spares tab's rows, the Roster's count and the notices with their seen flags. Core's Spares commands only delegate to it. Behind it, SpareRules is a private file of stateless helpers: the trimmed item string, whether an item can be traded, how Spares and Claims are stored in records, the caps and pruning, the item-gone decision and the winner's tie-break. See `docs/design/spares.md`.
- **Where** (`Core/Where.lua`): live spots between DATA. Every 2 s it reads `locate()`; while you move in the open world (more than 0.2% of the map since the spot last sent), the link is up, you aren't paused and others are online, a WHERE goes out to everyone: `{ character, mapId, x, y, at }` (positions to 0.01%, `at` never older than the own record's version, which can run ahead of the clock), one chunk, at most every `max(10, 3 × others online)` seconds, so about 20 whispers a minute at most whatever the Crew's size (OpenMap sends every 10 s). It never touches the record, so DIGESTs don't start asking for DATA; but if a WHERE went out since the record's version, the next DATA bumps the version so it wins over that WHERE. Received WHEREs are kept in memory per Member and used by `mapPins()` while they're for the shown Character and no older than its record. It also keeps the last open-world spot read, which a record entering an instance takes. Older BFFs ignore the type, so there's no protocol bump.
- **Doing** (`Core/Doing.lua`): what each Member is doing right now, for the Pocket Camp. Like a WHERE it is told as it happens, outside the record: when what you're doing changes, the link is up, you aren't paused and others are online, a DOING goes out to everyone: `{ doing, quest, at }`, one chunk, at most every `max(15, 5 × others online)` seconds (about 12 whispers a minute at most whatever the Crew's size), the latest state winning. The first DOING of a session goes out even when it says nothing, since the Crew may hold what the session before said. While something is being done it's said again every 2 minutes, and right after someone comes online. What's heard is held in memory per Member, runs out 5 minutes after it was last heard (the DOING that ends it can be lost) and goes when the Member goes offline. A state this version doesn't know counts as nothing, and older BFFs ignore the type. Tested through Core in `doing_spec`. See `docs/design/pocket-camp.md`.
- **Text** (`Core/Text.lua`): pure wording helpers the ready-to-render reads share: how long ago ("5m", "3h", "2d"), and a Feed day's title and a short date in local time, worked out from the server time and `utcOffset` since Core has no `date()`. Tested directly (`text_spec`).
- **Settle** (`Core/Settle.lua`): when sync has gone quiet after the link came up (10 s with no new DATA, at most 30 s). Feed uses it for While you were away, Goals for its silent baseline.
- **Goals** (`Core/Goals.lua`): the built-in Crew goal tracks and their rungs, progress worked out from Ledger's records, the reached rungs (which were quiet), the Crew's clears, the silent baseline, the Goals tab's rows and its trophies, and when the tab was last opened. See `docs/design/goals.md` and `docs/design/trophies.md`.
- **Clears** (`Core/Clears.lua`): the pure parts of Clears: which kill clears which instance (`Clears.FINAL_BOSSES`, from the dungeon table), how clears are kept in a record, and the Crew's clears over a list of records. Stateless, tested through Core. See `docs/design/trophies.md`.
- **PlayTimes** (`Core/PlayTimes.lua`): counts the own Member's seconds played per UTC hour of the week for the last 4 weeks, makes the summary their record shares, ages summaries by the viewer's clock and shifts them into local time. See `docs/design/play-times.md`.
- **Professions** (`Core/Professions.lua`): the pure parts of Professions: reading them from the game through the API handed in (secret values and errors keep the last list), how a list is stored in a record and checked, ranks, the Feed news between two lists (`Professions.news`: picked up, milestones, maxed), and the Professions tab from Roster's rows (`Professions.tab`). See `docs/design/professions.md`.
- **Catches** (`Core/Catches.lua`): the pure parts of Catches: the list of types and waters (data), reading a catch from the loot window through the API handed in (`Catches.read`), how catches are kept in a record (`Catches.add`, with the unlisted cap), the Crew's catches over the records, skipping anything malformed (`Catches.collect`, `Catches.typesCaught`), and what's news in them: rare finds (`Catches.rareHeld`, `Catches.rareFinds`) and While you were away's line (`Catches.newTypesLine`). Stateless, tested through Core, with `Catches.read` tested directly. See `docs/design/catches.md`.
- **Together** (`Core/Together.lua`): the dungeon table, and the Together tab from Roster's rows: which Characters show, who can play and who fits each dungeon (Members counted once), label rows and dungeon lanes, and what's shared with the Members picked. Pure and stateless, tested through `together()`. See `docs/design/together.md`.
- **Camp** (`Core/Camp.lua`): the Camp from Roster's rows and Feed's recent entries (`Feed:since`): who's in it and in what pose, graves and flowers, sparks, placement in art pixels (`Core.CAMP_LAYOUT`), what doesn't fit, and its wording on rows, the header and the popup's intro. Also the Pocket Camp (`Camp.pocket`): the online Members only, with their poses, and the room a flying figure's griffin takes. Pure and stateless, tested through `camp()` and `pocketCamp()`; who is fishing or at a profession is Core's, in memory, and what each Member said they're doing is Doing's. See `docs/design/camp.md` and `docs/design/pocket-camp.md`.
- **Roster** (`Core/Roster.lua`): builds panel rows from Ledger. Covers Main resolution, "on alt", online (heard within 12 min, and not seen leaving the channel since), Last seen, "can play with you" (±3 levels), the 30-day hide and sorting.
- **CrewCode** (`Core/CrewCode.lua`): generates, normalises and checks Crew codes, and derives the channel name and password from them.
- **Codec** (`Core/Codec.lua`): a plain-text protocol version header, then the LibSerialize + LibDeflate body (`2|<payload>`). A newer version is detected before anything is decoded. Protocol 2 is protocol 1's payload sent in Framing's chunks; protocol 1 is still read (`Codec.OLDEST`), so a friend on an older BFF is still seen.

## The link port

This is the only real seam in v1. Its adapters are the channel link and the fake link. The retail spike (`docs/research/channel-spike.md`) showed the channel carrying addon messages, but on WoW: Forever they are accepted and never delivered, so the channel link sends over a whisper mesh: the channel says who is online, and each message is whispered to each of them.

- Core → link: `send(string, to)`: to every other Character in the channel, or with `to` (a bare Character name) only to that one. **Best-effort**: a message can be lost silently, including chunks not yet sent when lockdown began or the friend left. The channel link sends a one-chunk message (every DIGEST) at `ALERT` priority, ahead of anything longer, which goes at `NORMAL` (see "Framing" below).
- Link → Core: `received(string)`, `up()`, `down()` and `gone(name)`. The sender's name is never passed with a message; identity travels inside the payload. Core drops messages carrying its own Member id (the fake link echoes your own messages back; whispers don't).
- `gone(name)`: a Character left the channel, i.e. logged out (a real logout leaves the channel before any goodbye could be sent, so there is none). The name is bare (`Ambiguate(sender, "none")`). Core marks the Member owning a Character of that name offline right away. On Forever the name is "First Last" while records hold only the first name, so the first name matches too (#152); two Characters sharing a first name may both go offline until the other's next message; the 12-minute timeout stays as the fallback. It is only a presence hint, never used to identify data.
- `sendFailed(name)`: a message from that Character was lost on the way (some of its chunks came and 30 s later the rest hadn't, see "Framing" below), or a chunk to that Character failed (anything but a throttle, which ChatThrottleLib retries itself: a general error, a logout, lockdown, or a Trial or Veteran account, which can't send addon messages since Forever 1.60.1 according to the wiki, not checked in game). Only that friend may have missed something, so the link stays up, replies owed to others stay owed, and Core sends that friend a DIGEST of their own 5 s later (at most one a minute per friend, since an account that can't send fails every time). If "No player named …" follows, or "Player is offline." within 3 s of a failed send to that one friend only (it names no one, so after failures to several it is put down to none of them), Presence drops them from its peers and the channel link calls `gone(name)`.
- Each adapter decides what "down" means. For the channel link it is `C_ChatInfo.InChatMessagingLockdown()`, or not yet in the Crew channel, or having left it, or Presence not ready (the channel's first member list not in yet, at most 5 s). A Character found in the channel later (the list is asked for again every minute) makes it go `down()` and straight back `up()`, so they get a fresh DIGEST.
- On every `up()`, Core sends a fresh DIGEST, plus its own DATA if its record changed while the link was down. This rule covers first join, rejoin and lockdown clearing; the DIGESTs below cover messages lost while it is up.
- Lockdown and Pause never appear in the port. Lockdown is the adapter's reason for being down. Pause is Core policy (Presence only sees that a Paused Member's Characters go silent). Don't gate sending on `AreOutgoingAddonChatMessagesRestricted()`, which the spike saw return true on accounts that sent fine; a Trial or Veteran account's failed sends only cost it a DIGEST a minute per friend.

### Presence

A **peer** is another Character known to be in the Crew channel, so one the channel link whispers. A peer is a Character, not a Member: Presence never sees a Member id, and a Member with two Characters online is two peers.

Presence (`Link/Presence.lua`) is pure and sits under the link port, inside the channel link. The channel link reads the game and tells it in plain names: we joined the channel (`start()`), the Crew changed (`stop()`), a member list's names without our own (`listed(names)`), a join or leave notice (`joined(name)`, `left(name)`), a BFF whisper from a name (`heard(name, message)`: a chunk, or a whole message from an older BFF; Presence hands it back with the name once the sender is a peer, and the channel link gives it to Framing), a whisper to a name entering the send queue and each chunk leaving it (`whispered(name)`, `chunk(name, queued, failed)`), "No player named …" for a name (`notFound(name)`), "Player is offline." (`offline()`), a notice it couldn't read (`unreadable()`, which only says how long after the last whisper it came, for the trace) and `tick()` once a second. It gets `now()` and holds no timers, so its timeouts are up to 1 s late.

What it answers and reports:

- **Who to whisper** (`targets(to)`): every peer, or the one named, leaving out the silent ones. `peer(name)` is the name a peer is whispered by, however the name given spells them.
- **Silence**: a peer who hasn't answered for 3 minutes isn't whispered until a BFF whisper from them is heard again. Every peer sends a DIGEST about every minute, so this is three missed in a row. It covers a peer who is unreachable with nothing saying so: a leave notice not recognised, or a notice the game won't let addons read (a friend in a dungeon). The 3 minutes count from the first whisper to them they haven't answered, and only while the link is up (`listening(isUp)`, from the channel link), since no one can be heard while it is down: coming out of a dungeon doesn't find everyone silent. A silent peer still gets one whisper every 5 minutes, and one as soon as the link comes back up (the DIGEST Core sends then), so two peers who lost each other's whispers at the same time don't both wait for the other to speak first. Silence never calls `gone(name)`: the peer stays a peer, and whether their Member shows as online stays the Roster's 12-minute rule. Consequence: a Member who has Paused sharing sends nothing, so after 3 minutes the others stop whispering them. They stop receiving updates while Paused (but for those few whispers), and catch up by DIGEST when they resume: their own DIGEST is heard, which ends the silence, and the replies bring what they missed. A Paused Member whispers no one, so no one goes silent for them.
- **Ready** (`ready()`, and `ready(why)` when it comes): the first member list since joining is in, or 5 s passed without one (a channel of one may get none). Joining again starts it over and forgets everyone.
- **Peers** come from a member list (which may arrive in parts, so a list only ever adds) and from join notices. They go on a leave notice, on "No player named …" for them, and on "Player is offline." within 3 s of a failed send to that one peer only. A peer dropped on "No player named …" is added again at once by a whisper from them or by their join notice, but not by a member list alone for 5 minutes: the list can go on showing a Character who logged out, and adding them back each minute would take the link down and up, send everyone a DIGEST and whisper them again every time.
- **Arrived**: a member list showed a new peer while ready. The channel link turns it into `down()` then `up()`.
- **Gone** (`gone(name)`): a peer left or was dropped, and any leave notice for the channel.
- **Strangers**: a whisper from a Character not known to be in the channel (usually one who just joined) is held, and a member list asked for. It is delivered when a list or a join notice shows them, and dropped after 10 s otherwise. At most 20 messages are held per stranger.
- **Whether a notice is ours**, for the chat filters, which keep no state of their own: "No player named …" for a peer, for one dropped for it in the last 30 s, or for a Character with a whisper still queued or a chunk sent in the last 30 s (a peer's leaving cancels neither, #160 and #178); "Player is offline." when it was just put down to a peer.

### Framing

The game carries 255 bytes in an addon whisper, and DATA is longer. BFF splits and reassembles messages itself (`Link/Framing.lua`, pure, under the link port like Presence; ADR 0007). AceComm's multipart did this before, with nothing in a chunk to say which message it belongs to or where: chunks arriving out of order, or one missing, gave a message that didn't decode (#163).

- **A chunk** is `2|`, then the message id, the chunk's index and the total (two base-62 digits each), then up to 247 bytes of the message (`Framing.ROOM`). Ids count up from a random start and wrap. The `2|` makes an older BFF read a chunk as a message of a newer protocol and show its out-of-date notice; it also means no chunk starts with a byte AceComm treats as multipart control (`\001`–`\004`), since AceComm still receives.
- **Reassembly** is per sender (the channel link names one by the key Presence compares names by, so "Name-Realm" and "name" are one) and message id, in any order, so two messages from one sender may interleave. A message is delivered only when every chunk is in. An id that comes back with another total, or with other text in a chunk already held, starts over (the sender reloaded and reused the id).
- **Lost:** a message with no new chunk for 30 s is dropped and reported (`lost(sender, got, total)`). The channel link calls `sendFailed(name)`, so Core sends that peer a DIGEST of its own and they send the DATA again. A sender who leaves, and everyone when the link goes down, is forgotten without a report.
- **Older BFF:** new still reads old. This version sends only chunks, but a whisper that doesn't start with `2|` is a whole protocol 1 message (AceComm put it together) and goes to Core as it is. An older BFF can't read the chunks: it shows the out-of-date notice and stops seeing updated friends until it updates. When reading protocol 1 is dropped isn't decided.
- **The outbox:** the channel link keeps the chunks still to send per peer and hands ChatThrottleLib one chunk of a long message at a time (the next when the callback for the one before comes), in a queue per peer. So a peer who leaves has their unsent chunks dropped (the one already handed over still goes, and may draw "No player named …"), as has everyone when the link goes down. When a chunk fails, the rest of that message is dropped. A one-chunk message goes to ChatThrottleLib at once, at `ALERT`, whatever is waiting.
- **The result code:** ChatThrottleLib's callback gives the game's `Enum.SendAddonMessageResult` for each chunk, which AceComm reduced to true or false. The trace shows it on a failed chunk. Which one Forever gives for a whisper to a logged-out friend isn't known yet.

## Sync: recovering lost messages

A message is lost without anyone knowing: a lost chunk loses the whole DATA, and nothing tells the sender (`docs/research/addon-message-reliability.md`). The receiver knows only if another chunk of it arrived. There are no ACKs (ADR 0006). Instead DIGESTs go out on their own, and a friend who missed something sees it in one and asks:

- **Confirming DIGEST:** 20–30 s after own DATA goes out, a DIGEST follows it. A friend who missed the DATA sees a newer version and replies with their own DIGEST, which makes the sender owe it. A lost ding arrives within about 40 s.
- **Every minute:** while the link is up, a DIGEST goes out 55–65 s after the last one (any DIGEST to everyone restarts the wait, the confirming one included).
- **After a failed send or a lost message:** that friend gets a DIGEST of their own (`sendFailed`, above).
- **"Later" changes** (XP, gold, Play times, professions, catches) go out within 60 s instead of waiting for the heartbeat.
- **Taking turns:** a DIGEST holds 10 entries (one chunk): the own record, then any ids a reply DIGEST is meant to fetch (with the version held, 0 if none, so whoever holds them replies), then the other records in turn by id, carrying on from where the last DIGEST stopped. In a Crew of more than 10 Members every record is listed within `ceil((Members − 1) / 9)` DIGESTs. One that left records out says `partial = true`, and a record it doesn't list isn't owed. Older clients ignore the flag (and owe whatever is missing, as before), and a DIGEST without it means what it always did, so mixed versions sync with no protocol bump. Every DIGEST from this version also says `turns = true`; one without it comes from an older client. Since an older client answers every DIGEST that leaves records out with DATA for all of them, the every-minute DIGEST is skipped while one was heard in the last 15 minutes and there are more than 10 records (confirming and per-friend DIGESTs still go out). In an idle Crew of 14 with two older clients, that keeps the busiest Member at 27 whispers a minute instead of 105.
- **In flight:** a record that went out to everyone (sent, or heard as DATA) in the last 2 s isn't owed to a DIGEST showing an older version: that DIGEST most likely crossed it on the way. A later DIGEST catches a real loss.
- **Traffic** (FakeNet, whispers sent a minute per Member, each chunk to each friend counted once; `BFF_TRAFFIC=1 busted tests/sync_spec.lua` prints them): a Crew of 4 idle, the busiest Member 4.5 (before this change 0.6); one Member grinding, 11.4 (2.1). A Crew of 6 idle, 7.5 (1.0); grinding, 25.0 (3.5). That is under one whisper every 2 s, against the server's allowance of about one addon message a second per prefix (which whispers outside instances may not even count) and ChatThrottleLib's 800 B/s. DOINGs aren't in these figures (the sim's Members do nothing); at their fastest they add `others × 60 / max(15, 5 × others)` whispers a minute, 4 in a Crew of 2 and 12 from a Crew of 4 up.

## Loading pure code in game and in tests

Every file starts with `local _, ns = ...` and attaches itself to `ns`, the addon's private table. Files in `Core/` only touch `ns`, Lua builtins, the `bit` library (WoW and LuaJIT both have it) and the pure libraries (LibSerialize, LibDeflate). Files in `Link/` only touch `ns` and Lua builtins. The test loader mimics the `.toc` with `loadfile("Core/Ledger.lua")("BFF", ns)`, for every `Core/` and `Link/` file. A luacheck rule bans WoW globals in `Core/` and `Link/`.

## Tests

- **Runner:** busted under LuaJIT, linted with luacheck.
- **The interface is the test surface.** Tests create Cores and check `rows()`, the While you were away summary, Feed entries, and the recorded listener events and sent messages. They never look inside `db`, Ledger or Gossip.
- **Pure, stateless helper files may be tested directly**, table-style, as `codec_spec` does for Codec, `text_spec` for Text, `spare_rules_spec` for SpareRules, `professions_spec` for reading professions and `catches_spec` for reading the loot window. Anything with state or lifecycle in Core is tested through Core; the game-facing files below are tested through their own interfaces.
- **Fake network** (`Dev/FakeNet.lua`):
  - One shared virtual clock and scheduler, so every run plays out the same way.
  - Each simulated client is a real Core with a fake link and its own `db`.
  - Per client: online or offline (link up or down), lockdown (link down while still online), Pause, reload (a new Core over the same `db`), and crash (a new Core over a copy of `db` taken at the last logout or reload).
  - Delivery is a broadcast to every client whose link is up (or, with `to`, a whisper to one), after a small delay, with optional drops (`drop`: lost, no one told) and failed sends (`fail`: the sender hears `sendFailed`) to test the best-effort contract.
  Delivery includes the sender itself, as the real channel does. A client going offline fires `gone(name)` on the others; a crash can skip it.
  - Messages go through the real Codec, and travel as the chunks the real Framing splits them into: each client reassembles what it receives. `chunked(chunks, from, to)` says which chunks of a message reach a client and in what order, to lose or reorder single chunks; a message left incomplete is reported lost 30 s later and the receiver's Core hears `sendFailed`, as from the channel link.
- **Scenarios** include:
  - C logs in after missing A's ding, learns it from B, and D stays quiet.
  - A crashes and its next version still wins.
  - Changes made during lockdown go out after one DIGEST when it clears.
  - A lost message is recovered at the next `up()`, and a lost ding within a minute while it stays up.
  - A failed send to one friend leaves the link up for the others and sends that friend a DIGEST of their own.
  - A message whose chunks arrive in another order is delivered; one with a chunk lost isn't, and the friend who missed it asks again.
  - XP and gold reach friends within a minute.
  - In a Crew of 14, every record is listed in a DIGEST within two rounds, and records left out make no one send DATA.
  - A Member on an older BFF (`tests/fixtures/legacy_gossip.lua`) syncs both ways, in a Crew of 3 and of 13.
  - Traffic stays well under the throttle in a Crew of 4 and of 6.
  - A removed Member is never shown or relayed.
  - Someone going quiet flips to offline after 12 minutes.
  - Ten Members with three Characters each: the DIGEST fits one message.
- **Framing** (`framing_spec`): splitting, reassembling in any order and interleaved, the 30 s loss report and what a chunk starts with, through Framing's own interface with a clock the spec moves.
- **Presence** (`presence_spec`): the rules above, through Presence's own interface with a clock the spec moves: no WoW stand-ins. `channel_link_spec` checks the wiring: a silent peer gets no whispers and Core hears no `gone`, a peer dropped as not found stays out when the list names them, a stranger's whisper is held, and the link comes up without a member list.
- **WoW stand-ins** (`tests/wow_stubs.lua`): for the game-facing files tested offline: the channel link (`channel_link_spec`: targeted sends, priorities, a chunk at a time, unsent chunks dropped when a peer leaves, chunks received in any order, a protocol 1 message still read, a lost message asking that peer again, failed sends, "Player is offline.", "No player named …" after a peer left with whispers queued, its trace lines and `state()`, with a stand-in secret value that errors if read), the sync log (`sync_log_spec`: the cap, saving and restoring) and the Report's text (`report_spec`). The file is loaded with the stand-ins as its globals, after the pure `Link/` files it builds on. UI frames aren't tested offline.
- **In game:** `/bff sim` reuses FakeNet to attach a few simulated Members to your real Core, so the panel and Feed can be tested without a friend online. Their records are kept and relayed like real ones, so it only runs in a Crew where no one else is known yet. `/bff sim ding` makes one ding, `/bff sim stop` logs them out. The `.toc` lists `Dev/` inside `#@do-not-package@`, so releases don't load it. Echo mode on the channel link loops your own messages back to you.
- **GitHub Actions** (`test.yml`) on every push and PR: `leafo/gh-actions-lua` (LuaJIT) and `leafo/gh-actions-luarocks`, `luarocks install busted luacheck`, fetch libraries, then `scripts/check.sh` (`luacheck`, then `busted`), the same command you run locally.
