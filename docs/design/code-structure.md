# Code structure and testing

Answers [How is the code split into modules and tested?](https://github.com/Shtian/bff-wow/issues/9). Builds on the sync resolution in #8 and `docs/adr/0001-owner-written-records-gossiped-by-server-time.md`. Domain vocabulary from `CONTEXT.md`; architecture vocabulary (module, interface, seam, adapter, depth) as in the `codebase-design` skill.

## The idea in one line

Almost all behaviour lives in one deep, pure-Lua module, **Core**, behind a small interface. The WoW-facing code is thin. Offline tests and `/bff sim` drive real Cores against each other through a fake link.

## Modules

| Module | Pure? | Owns |
|---|---|---|
| **Core** (`Core/`) | yes | Everything BFF knows and decides: Member records, sync, Feed, panel rows, saved-data layout. Details below. |
| **Snapshot** (`Game/Snapshot.lua`) | no | Reads the name (first, and the last name as UnitName's second value on Forever), level, XP, zone, class, gold, professions (through `Professions.read`) and GUID, counts deaths through `Deaths.record` (kept per Character in `BFF_CharacterDB`; each death counts once, and not in a battleground or arena), and calls `core:updateOwn(character)`. `Snapshot.locate()` reads where the Character stands, for Core's `locate`. `Snapshot.daylight()` reads the game's day or night, for Core's `daylight`, and on Forever's `DIEL_CYCLE_CHANGED` it calls `core:daylightChanged()`. `Snapshot.encounter(...)` turns `ENCOUNTER_END`'s payload into `encounterEnded()`'s, with the instance type and the group, secret values as nil. `Snapshot.catch()` reads the loot window through `Catches.read` on `LOOT_READY`, for `caught()`. It runs the Rare kill watch (`Rares.watch`) on the target, mouseover and nameplates seen, `LOOT_READY`, `PLAYER_TARGET_DIED`, `PLAYER_REGEN_ENABLED` and `PARTY_KILL`, calling `rareKilled()` for each kill and handing each read to `ns.rareSink` where a dev checkout sets one (`docs/design/rares.md`). `Snapshot.doing()` reads what the Character is doing right now, for `doing()`: in combat, at a vendor or the auction house (kept from `MERCHANT_SHOW`/`MERCHANT_CLOSED` and `AUCTION_HOUSE_SHOW`/`AUCTION_HOUSE_CLOSED`), away (`UnitIsAFK`), resting and flying, a secret value as false, and the shapeshift form (`GetShapeshiftFormID`, or Ghost Wolf's aura), a secret read as the last form read outside combat. It also calls `core:questHandedIn()` on `QUEST_TURNED_IN`. `Snapshot.party()` reads your party or raid (each unit's GUID, first and last name, a secret value as nil), for `encounterEnded()` and for `group()`, which it calls at start and on `GROUP_ROSTER_UPDATE`. |
| **Ruleset** (`Game/Ruleset.lua`) | no | Reads the Ruleset facts at login for Core's `ruleset` dep: `{ realmName, recordId, faction, serverId, name }` from `GetNormalizedRealmName`, `C_GameRules.GetCurrentGameModeRecordID`, `UnitFactionGroup`, the server ID in `UnitGUID("player")`, and the Ruleset's name from the player's own Battle.net rich presence (the text after `Forever - ` up to the next ` - `, `Ruleset.nameIn`). Each value is nil when the API is missing, errors or returns a secret value. Battle.net may not be ready at login, so App reads the name again on `BN_INFO_CHANGED` and hands it to `core:rulesetNamed(name)`. Tested offline (`ruleset_game_spec`). |
| **Bags** (`Game/Bags.lua`) | no | Offers a bag item as a Spare: the item on the cursor (the Spares tab's drop slot) or the first bag item matching a link (`/bff spares add`). Passes its item GUID and binding to `core:postSpare`, which refuses an item that can't be traded. Also tells Core where a posted item is now (`findItem`), for `core:bagsUpdated` on `BAG_UPDATE_DELAYED`. |
| **Channel link** (`Game/ChannelLink.lua`) | no | The production link adapter: joins and hides the Crew channel (including filtering its system notices out of chat), reads the member list, the join and leave notices and the "No player named …" and "Player is offline." notices and tells Presence (below), sends each message as addon whispers to the peers Presence names, puts a held stranger's chunks together in a second Framing and vouches for them to Presence when Core says the message is from a known Member (`fromKnownMember`), in the chunks Framing (below) splits it into, and decides when the link is up or down. It keeps what needs the game: joining and leaving, lockdown, checking that event arguments are readable (a secret value never reaches Presence), `Ambiguate`, the notice patterns, the player's own first and last name, ChatThrottleLib, AceComm's receiving side (it registers the prefix and puts an older BFF's multipart messages together) and the outbox: what is still to send per peer (see "Framing" under the link port). It holds no list of peers. A join counts only once the game sends `YOU_CHANGED` for the channel or its member list arrives, or BFF is already in it at start after a `/reload` (at login a channel number isn't proof, so BFF joins as usual): a channel number alone isn't proof. On a failed join (wrong password, too many channels, or a 10 s timeout with no channel number) it stays down and calls `joinFailed(kind)`. On `INVALID_NAME` for the Crew channel, on joining or later, it goes down with the reason "the game broke the channel" and calls `channelBroken()`; Core then moves the Crew to the next channel generation and `crewChanged` hands the link the new channel, or Core is at its cap and the link stays down. Its half of the sync trace (`setTrace(fn)`): each join attempt and how it ended, every notice for the Crew channel with its kind, arg 2 and arg 5 names and channel arguments, each message sent per Character with its bytes and chunks, each whisper received with its sender and bytes, a message of several chunks being whole, a message lost, each chunk's result (a failed one with the game's result code), unsent chunks dropped and why, the link going up or down and why, chat restriction changes, "No player named …" notices (one that names no peer with the peer keys it was compared with), "Player is offline." notices, a system message the game won't let it read within 5 s of a whisper (with the instance type and lockdown, never the text), entering and leaving an instance, leaving the group or it disbanding, the peers list changing and why, member lists, each with its name count, channel arguments and what became of it (taken, another channel's, before joining, or unreadable), once per channel arguments and verdict since joining, a peer going silent, being tried again and being heard again, and stranger whispers held or dropped. `state()` gives `{ up, reason, peers, instance, lockdown }` for `/bff report`; after a failed join the reason is "wrong password" or "too many channels" (`FAILURE_REASONS`). On Forever addon messages sent to a custom channel never arrive, so the channel only carries presence. See `docs/research/channel-spike.md`. |
| **Presence** (`Link/Presence.lua`) | yes | Who is in the Crew channel and can be whispered: the peers, held strangers, whether the first member list is in, and whether a chat notice is about one of ours. Decodes no messages and knows nothing about Members. See "Presence" under the link port. Tested through its own interface (`presence_spec`). |

The first draft's Zones module is dropped from v1, because only the overlap finder needed it. The overlap finder (the Dungeons tab) works from levels and a dungeon table instead.

## Core

### Interface

Core is created with:

- `db`: the whole `BFF_DB` table. Core owns its layout, defaults and migrations, settings included. Core keeps it as `self.account` (settings, What's new and the first-install check) and keeps the active Crew's slot, `BFF_DB.crews[slotId]`, as `self.db` (ADR 0009, `docs/design/crews-per-ruleset.md`). Leaving sets the slot aside as the ruleset's left slot and binds a fresh one; rejoining its code binds it again (`docs/design/joining-a-crew.md`). The layout:
  - **The account** (the top level): settings, the panel and Pocket Camp positions, the minimap button, the together and catches settings, and What's new state (`changesSeen`, `changesTold`, `newerBffTold`). Settings are shared by every Ruleset; only Appear offline (`paused`) is saved in the slot.
  - **`crews[slotId]`**: one Crew's data. Its Ruleset key (nil while unclaimed) and `provisional` flag, the Crew code and channel moves, the Member id and records, the Feed, goals, Spares, Appear offline, play times and the stray.
  - **`rulesets[key]`**: the `active` slot, the `left` slot if any, and the record ID, faction, name and server IDs that repair a changed key.

  The full layout is in `docs/design/crews-per-ruleset.md`.
- `ruleset` (optional): the facts that pick the slot: `{ realmName, recordId, faction, serverId, name }`, each optional, read by `Game/Ruleset.lua` in game. Core cleans them with `Slots.facts`. The key is `realm:<realm name>:<faction>` when there's a realm name (retail), else `mode:<record ID>:<faction>` (Forever), else `default`. With none the key is `default`, so tests and the dev sim keep one slot. `rulesetNamed(name)` saves a name that arrives after login and fires `changed`. `elsewhere()` is the no-Crew card's read, with its finished lines: `hint` (where your other Crews are), `ask` (the question about a Crew from before Rulesets that BFF can't place) and `offer` (the other faction's provisional Crew), each nil when it doesn't apply. The panel and the login chat line both show these lines. They're answered by `placeCrewHere()`, `startFresh()` and `bringCrewHere()`; see `crews-per-ruleset.md`. `ruleset()` reads back the key, the realm name and current server ID from the facts, the saved record ID, faction, server IDs and name, whether the slot is `provisional`, and the key repair made this login as finished text (`repair`, like "mode:15:Alliance moved to mode:20:Alliance (by server ID)"), which also goes to the sync log once `setTrace` is called.
- `now()` and `random()`: the clock (`GetServerTime` in game) and randomness, so tests are deterministic.
- `link`: the outgoing half of the link port (`send(string, to)`), and optionally `inChannel(name)`: whether a Character of that bare name is in the Crew channel now.
- `listener`: receives Core's events.
- `initialLogin`: `isInitialLogin` from `PLAYER_ENTERING_WORLD`, so Core can tell a login from a reload (see `docs/design/feed.md`).
- `maxLevel`: from `GetMaxLevelForPlayerExpansion()`, for max level Feed entries.
- `utcOffset`: how many seconds local time is ahead of server time, so `feed()` starts each day at local midnight and `playTimes()` shows local hours (default 0).
- `daylight()` (optional): what the game says about day and night, as `Snapshot.daylight()` reads it: `C_DateAndTime.IsDayTime()`'s boolean, or nil and `GetGameTime()`'s hour and minute where that API doesn't exist. `phase()` reads it on each Camp read (`docs/design/camp.md`, Day and night).
- `locate()` (optional): where the Character being played stands, as `Snapshot.locate()` reads it: `{ mapId, x, y }` in the open world, `{ instance }` inside an instance, or nil when it can't be read. Core calls it just before its own DATA goes out (a zone change, a ding, the heartbeat), and every 2 s for Where (below), so moving never changes the record or sends DATA; it sends a small WHERE instead. The Ledger rounds the position to 0.1%, keeps the last open-world spot read (or the record's) inside an instance, and keeps the last known spot on nil.
- `itemLink(itemString)` (optional): the game's link for an item string, as `Snapshot.itemLink` reads it, or nil while the item isn't cached. Spare texts say "an item" until then (`docs/design/spares.md`).
- `itemLook(itemId)` (optional): how the game shows an item, as `Skin.itemLook` reads it: `{ text, icon, edge }`, the name in its quality colour, the icon and the quality colour, each nil while it isn't cached. Rare finds use the English name until then (`docs/design/feed.md`).
- `findItem(itemGuid)` (optional): where a posted item is now, as `Bags.findItem` reads it: whether it's in the bags or bank (nil if the game can't say), and whether it's equipped.
- `finalBosses` (optional): encounter ID to instance name, the kills that are Clears. Defaults to `Core.FINAL_BOSSES`, from the dungeon table's `finals`; tests and the dev sim pass their own, since the datamined IDs are unconfirmed.
- `version` (optional): the .toc's Version (`v2.3.0`; a checkout's `dev` counts as none). It goes into the own record as `bff`, and What's new reads changes up to it.
- `changelog` (optional): the newest releases of `CHANGELOG.md`, as `ChangelogText.lua` carries them in a release build (nil in a checkout), for What's new (`docs/design/whats-new.md`).
- `gossip` (optional): the Gossip module to use. Only FakeNet passes one, for a client that syncs like an older BFF (`tests/fixtures/legacy_gossip.lua`).

Inputs:

- `updateOwn(character)`: the current state of the Character being played, from Snapshot.
- `tick()`: once a second. Core decides what is due (reply delays, debounced sends, heartbeat, online timeouts, pruning), and counts the second towards Play times.
- `received(string, from)`, `up()`, `down()`, `gone(name)`, `sendFailed(name)`, `joinFailed(kind)` and `channelBroken()`: the incoming half of the link port. `fromKnownMember(string)`: whether a message is from another Member whose record is held and who isn't removed (a Member who left counts), which the channel link asks about a stranger's whisper.
- `bagsUpdated()`: on each `BAG_UPDATE_DELAYED`, never before the first of a session. Core checks where each own Spare's item is (ADR 0004).
- `caught(loot)`: on `LOOT_READY` (a loot window's catch once), from `Snapshot.catch`: `{ items, zone, subzone, mapId }`, or nil when the loot isn't from fishing. Each item goes into the own record as a Catch, shared with the next send, or now for a rare find, which makes a Feed entry. Types caught can reach a Crew goal step (`docs/design/catches.md`).
- `rareKilled(kill)`: from the Rare kill watch Snapshot runs (`Rares.watch`): `{ npcId, unlisted, name, zone, subzone, mapId }`. The first kill of each Rare goes into the own record (an unlisted rare up to a cap), out now for a listed one, with the next send for an unlisted one. In a Crew, the Crew's first kill of a Rare is a trophy and a Crew-wide Feed entry, and Rares slain can reach a step (`docs/design/rares.md`).
- `doing(facts)`: every second, from `Snapshot.doing`: `{ combat, vendor, auction, afk, resting, flying }`, each true or not, and `form` (`wolf`, `bear`, `cat`, `travel`, `seal`, `moonkin` or nil). Core picks the one to show (flying, the auction house, a vendor, fighting, which lasts 20 s past the end of combat, then away, then resting), shows it on your figure in the Pocket Camp and tells the Crew with a DOING when it changes (Doing, below), and shows the form on your figure at once. The record doesn't change.
- `questHandedIn()`: on `QUEST_TURNED_IN`. The Pocket Camp plays the quest animation on your figure, and the next DOING tells the Crew, if it goes out within 90 s.
- `group(party)`: at start and on `GROUP_ROSTER_UPDATE`, from `Snapshot.party`: `{ guid, name, lastName }` per unit, you included. Held in memory for the Pocket Camp, which seats the Members in it next to you; fires `changed` when it differs. Nothing is sent.
- `encounterEnded(encounter)`: on `ENCOUNTER_END`, from `Snapshot.encounter`: `{ encounterId, success, instanceType, party }`. A known final boss killed in a party or raid instance, in a Crew, is a Clear in the own record (ADR 0005); returns the instance's name, or nil and why not (`docs/design/trophies.md`).
- Commands: start, join and leave a Crew, change the display name, Set as Main, Remove and re-add a Member, Pause sharing, and settings (see `docs/design/joining-a-crew.md`). Spares: post (with the item's GUID, kept locally, and its binding: an item that can't be traded is refused), withdraw and Give one, and make and withdraw a Claim (`docs/design/spares.md`).

Outputs:

- `link.send(string)`: best-effort (see the link port below).
- Listener events:
  - `changed`: re-read whatever you show (`rows()`, `feed()` and the rest). Also fires when a Member passes the 12-minute online timeout (going offline, or quiet while still in the channel), or is heard again, even though no record changed. Settings don't fire it.
  - `settingChanged(key, value)`: a setting really changed (setting a value it already has fires nothing). App passes it to Panel, PocketCamp, Minimap, Toasts and MapPins, and each ignores keys it doesn't use: Toasts clears its queue when `toasts` turns off, Minimap shows or hides the button on `minimap`, Panel redraws on `paused` (its footer status), `camp` and `seasons`, and moves, resizes and redraws on `panelPlace`, and on any key while its Settings view is open, PocketCamp redraws on `camp`, `seasons` and every `pocketCamp*` key, and MapPins redraws on `mapPins`, `mapPinSize` and `camp`.
  - `feedEntry(entry, outlets)`: a Live event from the Feed. While the Camp is on, an entry about a Member the Roster shows has `figure`, that Member's shown class, for the toast. Core decides where it goes: `outlets` is `{ chat, toast }`, from the chat-line and toast settings, and App prints `entry.text` and shows a toast exactly as told, reading neither setting. With both off it isn't fired, and the entry stays unseen for While you were away.
  - `pocketCampAnimation(animation)`: a new Feed entry the Pocket Camp animates, made while running: `{ kind, memberId }`, kind "ding", "maxLevel", "death" or "rareFind" for a Member by its fire, or "goal" (no `memberId`) for the fire; also "quest", for a Member who handed in a quest (from a DOING, or your own), and "arrive", for a Member who came online. Fired only while the Pocket Camp shows, whatever the chat-line and toast settings are, and it marks nothing seen (`docs/design/pocket-camp.md`).
  - `campReaction(reaction)`: a Reaction this client just attached, for the Camps to play: `{ kind, memberId, grave }`, kind "cheer", "respects" or "welcome", memberId whose entry it is, grave (Respects only) the key of the Grave to bloom. Fired once sync has settled, never on first sight, for a Removed Member's or on a Removed or Left Member's entry, for Respects after the first, or with the Camp off; your own Respects and Welcome too, your own Cheer not (UI hops it). Whatever the chat-line and toast settings are, and it marks nothing seen (`docs/design/camp.md`, Reactions, live).
  - `reaction(news, outlets)`: a live Reaction to one of your entries, fired and shown the same way as `feedEntry`. Toasts for the same entry merge (see `docs/design/reactions.md`).
  - `spare(news, outlets)`: a live Spare notice (a Claim now winning yours, or one Given to you), fired and shown the same way as `feedEntry` (see `docs/design/spares.md`).
  - `spareGone(gone)`: at the first bag check after a real login, a Spare whose item is gone was withdrawn (`action` "withdrawn": App says so in chat) or has a Claim (`action` "ask", with its `winner`: App asks whether to Give or withdraw it).
  - `awaySummary(summary)`: While you were away has settled after an initial login. Fired only when the popup setting is on and it isn't empty. App shows it once out of combat. It comes worded, so the popup only lays it out: the scoreboard's `intro` ("2 things happened while you were away."), the `maxLevel` its level bars run to, each Character's `label` ("Alt Jaina", the Main's name, or nil for a Main named like the Member) and `gained` ("+2" or "new"), each Member's `tags` (`{ text, highlight }` for joined and left), a `highlight` flag on each profession line, and `catches`: the line of new types others caught, then the rare finds missed. With the Camp on, `camp` is the Camp at `Core.CAMP_LAYOUT.awayColumns` without the tent, each actor with `gained` (its Main's, as the scoreboard words it; nil with nothing gained) and `highlight` (max level), and `intro` reads "The fire kept burning. 7 things happened in camp."
  - `moved`: a Member's live spot changed (a WHERE). App redraws only the map pins, and only while the map is open (it redraws on opening).
  - `newerBff(line)`: a Member in the Crew runs a newer release than yours, said once per version (`docs/design/whats-new.md`): `{ version, members, text }`, the highest version, the display names of the Members on it, and the worded line App prints in chat.
  - `notice(kind)`: one-off messages ("BFF is out of date", "you left the Crew").
  - `crewChanged`: the Crew was joined or left, moved to another channel generation, Appear offline was turned on or off, or a leave began while appearing offline. App tells the channel link to join or leave the channel from `channel()`.
- Settings: Core holds one ordered list of the local settings (`docs/design/settings-and-release.md`). `setting(key)` reads one and `setSetting(key, value)` sets it; `settings()` is the Settings page's ready-to-render read, a section per `{ title, settings }`, each setting `{ key, kind, label, value }`, plus `choices` (`{ key, label }`) for a `choice` and `needs` (the on/off setting it's greyed out without). The named methods (`isPaused()`/`setPaused()`, `isMinimapShown()`/`setMinimapShown()`, `isChatLinesOn()`/`setChatLines()`, `isAwayPopupOn()`/`setAwayPopup()`, `isToastsOn()`/`setToasts()`, `toastSound()`/`setToastSound()` and `toastPosition()`/`setToastPosition()`) are one-line wrappers over these. `setPanelPlace(width, height, left, top)` and `resetPanelPlace()` save the panel's size and position (clamped to its limits, `Core.PANEL_MIN_*`/`PANEL_MAX_*`), and `panelPlace(screenWidth, screenHeight)` says where it opens on this screen: shrunk to fit, moved onto it, and with nil `left`/`top` for centred. `minimapIcon()` is the saved table LibDBIcon keeps the button's position and the minimap setting's hidden flag in. `setPocketCampPosition(x, y)`, `setPocketCampScale(scale)` and `setPocketCampColumns(columns)` save where the Pocket Camp was dragged to, how big it is and how wide it can grow; `Core.pocketCampWidth(columns)` and `Core.pocketCampSeats(columns)` give the nearest of its widths and how many figures fit at one, for its grip.
- What's new: `hasNewChanges()` says whether changes in BFF since you last looked haven't been seen (the sidebar's version label's dot). `openWhatsNew()` starts a visit on every draw of the view, marking every change seen (and fires `changed` when that changed anything), but the releases new when it opened stay new in `whatsNew()` until `leaveWhatsNew()`. `whatsNew()` is the view ready to render (`{ title, line, updateNotice, releases, older }`, nil without a changelog), with `updateNotice` naming the Members known to run a BFF older than a major release new on this visit. The `awaySummary` summary gets `update` (`{ title, lines, more }`, finished text) once per update, taken even with the popup off so it's never kept for later, and an update alone makes a summary (`docs/design/whats-new.md`).
- Reads: `crew()` (code, channel name and password for the current channel generation, a `leaving` flag while a leave is pending, `alone` while no other Member is known, `capped` once the game has broken 5 channels this session, `generation`, `generationFrom` ("saved", "moved this session" or "<name>'s record") and `moves` (moves this session) for `/bff report`, and `status`: the Roster footer's finished line, the first that applies of leaving, no channel left to try, appearing offline and waiting for your Crew, else nil; `waiting` when the alone card shows it instead; `joined` when you joined the Crew rather than started it; all from the active slot, so nil outside a Crew, after a leave, and on a Ruleset where you have none), `channel()` (the `crew()` the channel link should be in: nil while appearing offline, unless a leave is pending), `displayName()` and `joinFailure()` (the last failed join's `kind` and `at`, saved until the link is next up, for `/bff report`).

### Inside Core

These are internal seams: separate files for locality, tested only through Core's interface, with nothing swappable behind them. The one exception is the `gossip` dep, so mixed-version tests can run a client with an older BFF's Gossip.

- **Ledger** (`Core/Ledger.lua`): what we know. Holds the own record and copies of everyone else's, the merge rule (a higher version wins), the Remove list, the "left" flag, last-heard times, and 180-day pruning. It stores and writes records (versions, the bump, what Gossip sends) and prunes on every own write, but never reads the Spares layout: the Spares module writes its part of the own record through `changeOwn`, and prunes it through the pruner it hands over with `pruneWith` at setup, since only Spares knows which Spares and Claims have ended. Removing a Member deletes their record and drops future copies, but keeps the last version seen: a refused copy that is newer raises it. The DIGEST lists removed Members with that version, in turn with the held records, so no peer owes them to you (one removed before versions were kept is listed with 0 and sent once more). Re-adding takes them off the list and forgets the version, then sends a DIGEST, and peers reply with DATA.
- **Gossip** (`Core/Gossip.lua`): when to talk. Owns the DIGEST and DATA rules, 1–4 s reply delays, who a reply goes to (the sender of the DIGEST only, see Sync below), send timing (immediate, 10 s zone debounce, "later" changes such as XP within 60 s, 5-minute heartbeat), the DIGESTs that recover lost messages (see Sync below), the "record changed" flag, the replies owed per peer, and Pause.
- **Feed** (`Core/Feed.lua`): turns a before/after record pair from Ledger into Feed entries, including skipped versions such as 22 → 24. For others' "gave" entries it asks Spares (`Spares.newlyGiven`) what was newly Given between the two; your own come from Spares when you Give. Feed owns how a "gave" entry looks. Also owns the capped log, seen flags, and when While you were away is ready. See `docs/design/feed.md`.
- **Reactions** (`Core/Reactions.lua`): the pure parts of Reactions: which Reaction each entry kind has, the key a Reaction points at an entry by, how keys are stored in a record and pruned, and the wording the owner sees. Feed attaches Reactions to its entries. See `docs/design/reactions.md`.
- **Spares** (`Core/Spares.lua`, with `Core/SpareRules.lua`): the whole Spare lifecycle, and the only Spare interface Core uses. Owns posting, withdrawing and Giving, making and withdrawing Claims, expiry, who wins (ADR 0003), the item-gone state and bag check (ADR 0004), the item GUIDs of own Spares (local only), the Spares tab's rows, the Roster's count and the notices with their seen flags. Core's Spares commands only delegate to it. Behind it, SpareRules is a private file of stateless helpers: the trimmed item string, whether an item can be traded, how Spares and Claims are stored in records, the caps and pruning, the item-gone decision and the winner's tie-break. See `docs/design/spares.md`.
- **Where** (`Core/Where.lua`): live spots between DATA. Every 2 s it reads `locate()`; while you move in the open world (more than 0.2% of the map since the spot last sent), the link is up, you aren't paused and others are online, a WHERE goes out to everyone: `{ character, mapId, x, y, at }` (positions to 0.01%, `at` never older than the own record's version, which can run ahead of the clock), one chunk, at most every `max(10, 3 × others online)` seconds, so about 20 whispers a minute at most whatever the Crew's size (OpenMap sends every 10 s). It never touches the record, so DIGESTs don't start asking for DATA; but if a WHERE went out since the record's version, the next DATA bumps the version so it wins over that WHERE. Received WHEREs are kept in memory per Member and used by `mapPins()` while they're for the shown Character and no older than its record. It also keeps the last open-world spot read, which a record entering an instance takes. Older BFFs ignore the type, so there's no protocol bump.
- **Doing** (`Core/Doing.lua`): what each Member is doing right now, for the Pocket Camp. Like a WHERE it is told as it happens, outside the record: when what you're doing changes, the link is up, you aren't paused and others are online, a DOING goes out to everyone: `{ doing, form, quest, at }`, one chunk, at most every `max(15, 5 × others online)` seconds (about 12 whispers a minute at most whatever the Crew's size), the latest state winning. The first DOING of a session goes out even when it says nothing, since the Crew may hold what the session before said. A shapeshift form is due as soon as you shift (a travel form once held for 30 s), and its end never is. While something is being done, or a form held, it's said again every 2 minutes, and right after someone comes online. What's heard is held in memory per Member, runs out 5 minutes after it was last heard (the DOING that ends it can be lost) and goes when the Member goes offline; a form runs out 2.5 minutes after it was heard. A state or form this version doesn't know counts as nothing, a DOING without `form` has none, and older BFFs ignore the type. Tested through Core in `doing_spec`. See `docs/design/pocket-camp.md`.
- **Text** (`Core/Text.lua`): pure wording helpers the ready-to-render reads share: how long ago ("5m", "3h", "2d"), a Feed day's title, a short date and the month and day (`monthDay`) in local time, worked out from the server time and `utcOffset` since Core has no `date()`. Tested directly (`text_spec`).
- **Settle** (`Core/Settle.lua`): when sync has gone quiet after the link came up (10 s with no new DATA, at most 30 s). Feed uses it for While you were away, Goals for its silent baseline.
- **Goals** (`Core/Goals.lua`): the built-in Crew goal tracks and their rungs, progress worked out from Ledger's records, the reached rungs (which were quiet), the Crew's clears and Rare kills, the silent baseline, the Trophies tab's rows and its trophies, and when the tab was last opened. See `docs/design/goals.md` and `docs/design/trophies.md`.
- **Deaths** (`Core/Deaths.lua`): which deaths count, and counting each once. `Deaths.counts` says from the instance type: all but those in a battleground (`pvp`) or arena. `Deaths.died` counts a death and marks it `deathCounted`, so a second `PLAYER_DEAD` for the same death (the game fires two when a Character dies with a pet out) doesn't count again. `Deaths.checkAlive` clears the mark once the Character is neither dead nor a ghost, so releasing to a ghost keeps it. ## The link port

This is the only real seam in v1. Its adapters are the channel link and the fake link. The retail spike (`docs/research/channel-spike.md`) showed the channel carrying addon messages, but on WoW: Forever they are accepted and never delivered, so the channel link sends over a whisper mesh: the channel says who is online, and each message is whispered to each of them.

- Core → link: `inChannel(name)`: whether a Character of that bare name is in the Crew channel (the channel link asks Presence, `has(name)`). A Member heard since their last logout (or since your login: at login `heard` starts empty, so a Character the member list still shows after logging out isn't taken for online) stays online while one of their Characters is there, even silent past 12 minutes: in a battleground the game keeps their BFF from sending, but they stay in the channel. They go offline on `gone(name)`: a leave notice, or a whisper bouncing, which a silent peer gets every 5 minutes. Core asks for each Character's name and, with a last name, "First Last".
- Core → link: `send(string, to)`: to every other Character in the channel, or with `to` (a bare Character name) only to that one. **Best-effort**: a message can be lost silently, including chunks not yet sent when lockdown began or the friend left. The channel link sends a one-chunk message (every DIGEST) at `ALERT` priority, ahead of anything longer, which goes at `NORMAL` (see "Framing" below).
- Link → Core: `received(string, from)`, `up()`, `down()`, `gone(name)`, `joinFailed(kind)` and `channelBroken()`, and one read, `fromKnownMember(string)` (see Strangers under Presence). `from` is the sender's bare Character name, the same form `send(string, to)` takes: the channel link has it from the whisper, the fake link from the sending client. It is only an address for the reply (see "Replies go to the sender" under Sync). Identity still travels inside the payload, never in `from`. With no `from`, Core replies to everyone. Core drops messages carrying its own Member id (the fake link echoes your own messages back; whispers don't).
- `joinFailed(kind)`: the link can't join the Crew channel (`wrongPassword` or `tooManyChannels`) and won't come up for this Crew. Core shows the notice, saves the failure until the next `up()`, and finishes a pending leave without sending (see Leaving in `docs/design/joining-a-crew.md`). The fake link never fails a join.
- `channelBroken()`: the game broke the Crew channel (ADR 0008). Core moves to the next channel generation, saves it, writes it into your own record and fires `crewChanged`, at most 5 times a session (counted again from the next login). Past that it sets `capped`, says so once in chat (`notice` `noChannel`) and finishes a pending leave. Core also moves up, never down, whenever a current Member's record carries a higher generation, at login and on DATA.
- `gone(name)`: a Character left the channel, i.e. logged out (a real logout leaves the channel before any goodbye could be sent, so there is none). The name is bare (`Ambiguate(sender, "none")`). Core marks the Member owning a Character of that name offline right away, and drops whatever reply it owed that Character. On Forever the name is "First Last" while records hold only the first name, so the first name matches too (#152); two Characters sharing a first name may both go offline until the other's next message; the 12-minute timeout stays as the fallback. It is only a presence hint, never used to identify data.
- `sendFailed(name)`: a message from that Character was lost on the way (some of its chunks came and 30 s later the rest hadn't, see "Framing" below), or a chunk to that Character failed (anything but a throttle, which ChatThrottleLib retries itself: a general error, a logout, lockdown, or a Trial or Veteran account, which can't send addon messages since Forever 1.60.1 according to the wiki, not checked in game). Only that friend may have missed something, so the link stays up, replies owed to others stay owed, and Core sends that friend a DIGEST of their own 5 s later (at most one a minute per friend, since an account that can't send fails every time). If "No player named …" follows, or "Player is offline." within 3 s of a failed send to that one friend only (it names no one, so after failures to several it is put down to none of them), Presence drops them from its peers and the channel link calls `gone(name)`.
- Each adapter decides what "down" means. For the channel link it is `C_ChatInfo.InChatMessagingLockdown()` (which turns true only after the restriction event, so the link checks again a frame later and every second, and `send` and `state()` treat a lockdown not yet noticed as down), or not yet in the Crew channel, or having left it, or Presence not ready (the channel's first member list not in yet, at most 5 s). A Character found in the channel later (the list is asked for again every minute) makes it go `down()` and straight back `up()`, so they get a fresh DIGEST.
- On every `up()`, Core sends a fresh DIGEST, plus its own DATA if its record changed while the link was down. This rule covers first join, rejoin and lockdown clearing; the DIGESTs below cover messages lost while it is up.
- Lockdown and Pause never appear in the port. Lockdown is the adapter's reason for being down. Pause is Core policy: `channel()` is nil while Paused (unless leaving the Crew), so the App hands the link no channel, the link leaves it, and others get `gone` and show you offline at once. A Paused Member hears nothing until they resume, and catches up with the usual DIGEST on `up()`. Don't gate sending on `AreOutgoingAddonChatMessagesRestricted()`, which the spike saw return true on accounts that sent fine; a Trial or Veteran account's failed sends only cost it a DIGEST a minute per friend.

### Presence

A **peer** is another Character known to be in the Crew channel, so one the channel link whispers. A peer is a Character, not a Member: Presence never sees a Member id, and a Member with two Characters online is two peers.

Presence (`Link/Presence.lua`) is pure and sits under the link port, inside the channel link. The channel link reads the game and tells it in plain names: we joined the channel (`start()`), the Crew changed (`stop()`), a member list's names without our own (`listed(names)`), a join or leave notice (`joined(name)`, `left(name)`), a BFF whisper from a name (`heard(name, message)`: a chunk, or a whole message from an older BFF; Presence hands it back with the name once the sender is a peer, and the channel link gives it to Framing), a held stranger the channel link vouches for (`vouched(name)`, see Strangers below; `holds(name)` says whether one is held), a whisper to a name entering the send queue and each chunk leaving it (`whispered(name)`, `chunk(name, queued, failed)`), "No player named …" for a name (`notFound(name)`), "Player is offline." (`offline()`), a notice it couldn't read (`unreadable()`, which only says how long after the last whisper it came, for the trace) and `tick()` once a second. It gets `now()` and holds no timers, so its timeouts are up to 1 s late.

What it answers and reports:

- **Who to whisper** (`targets(to)`): every peer, or the one named, leaving out the silent ones. `peer(name)` is the name a peer is whispered by, however the name given spells them.
- **Silence**: a peer who hasn't answered for 3 minutes isn't whispered until a BFF whisper from them is heard again. Every peer sends a DIGEST about every minute, so this is three missed in a row. It covers a peer who is unreachable with nothing saying so: a leave notice not recognised, or a notice the game won't let addons read (a friend in a dungeon). The 3 minutes count from the first whisper to them they haven't answered, and only while the link is up (`listening(isUp)`, from the channel link), since no one can be heard while it is down: coming out of a dungeon doesn't find everyone silent. A silent peer still gets one whisper every 5 minutes, and one as soon as the link comes back up (the DIGEST Core sends then), so two peers who lost each other's whispers at the same time don't both wait for the other to speak first. Silence never calls `gone(name)`: the peer stays a peer, and whether their Member shows as online stays the Roster's 12-minute rule. Consequence: a Member who has Paused sharing sends nothing, so after 3 minutes the others stop whispering them. They stop receiving updates while Paused (but for those few whispers), and catch up by DIGEST when they resume: their own DIGEST is heard, which ends the silence, and the replies bring what they missed. A Paused Member whispers no one, so no one goes silent for them.
- **Ready** (`ready()`, and `ready(why)` when it comes): the first member list since joining is in, or 5 s passed without one (a channel of one may get none). Joining again starts it over and forgets everyone.
- **Peers** come from a member list (which may arrive in parts, so a list only ever adds) and from join notices. They go on a leave notice, on "No player named …" for them, and on "Player is offline." within 3 s of a failed send to that one peer only. A peer dropped on "No player named …" is added again at once by a whisper from them or by their join notice, but not by a member list alone for 5 minutes: the list can go on showing a Character who logged out, and adding them back each minute would take the link down and up, send everyone a DIGEST and whisper them again every time.
- **Arrived**: a member list showed a new peer while ready. The channel link turns it into `down()` then `up()`.
- **Gone** (`gone(name)`): a peer left or was dropped, and any leave notice for the channel.
- **Strangers**: a whisper from a Character not known to be in the channel (usually one who just joined) is held, and a member list asked for. It is delivered when a list or a join notice shows them, or when the channel link vouches for them, and dropped after 10 s otherwise. At most 20 messages are held per stranger. The channel link vouches for a stranger once their whispers make a whole message (put together by a second Framing, `strangerFraming`, apart from the one for peers, since the held chunks go through that one when they become a peer) and Core says it is from a known Member (`fromKnownMember(message)`: a Member whose record is held, not your own and not removed; one who left counts, since one who whispers you is rejoining). This keeps a friend reachable on a client that gets no member list. It is a mitigation, not a cure: two such clients never find each other, since neither whispers first; a client that knows no other Member yet (a new joiner) still drops everyone; and a friend found this way may be found only after up to 5 minutes, by their silent-peer retry. Trace: `peer added: <name> (known Member)`.
- **Whether a notice is ours**, for the chat filters, which keep no state of their own: "No player named …" for a peer, for one dropped for it in the last 30 s, or for a Character with a whisper still queued or a chunk sent in the last 30 s (a peer's leaving cancels neither, #160 and #178); "Player is offline." when it was just put down to a peer.

### Framing

The game carries 255 bytes in an addon whisper, and DATA is longer. BFF splits and reassembles messages itself (`Link/Framing.lua`, pure, under the link port like Presence; ADR 0007). AceComm's multipart did this before, with nothing in a chunk to say which message it belongs to or where: chunks arriving out of order, or one missing, gave a message that didn't decode (#163).

- **A chunk** is `2|`, then the message id, the chunk's index and the total (two base-62 digits each), then up to 247 bytes of the message (`Framing.ROOM`). Ids count up from a random start and wrap. The `2|` makes an older BFF read a chunk as a message of a newer protocol and show its out-of-date notice; it also means no chunk starts with a byte AceComm treats as multipart control (`\001`–`\004`), since AceComm still receives.
- **Reassembly** is per sender (the channel link names one by the key Presence compares names by, so "Name-Realm" and "name" are one) and message id, in any order, so two messages from one sender may interleave. A message is delivered only when every chunk is in. An id that comes back with another total, or with other text in a chunk already held, starts over (the sender reloaded and reused the id).
- **Lost:** a message with no new chunk for 30 s is dropped and reported (`lost(sender, got, total)`). The channel link calls `sendFailed(name)`, so Core sends that peer a DIGEST of its own and they send the DATA again. A sender who leaves, and everyone when the link goes down, is forgotten without a report.
- **Older BFF:** new still reads old. This version sends only chunks, but a whisper that doesn't start with `2|` is a whole protocol 1 message (AceComm put it together) and goes to Core as it is. An older BFF can't read the chunks: it shows the out-of-date notice and stops seeing updated friends until it updates. When reading protocol 1 is dropped isn't decided.
- **The outbox:** the channel link keeps the chunks still to send per peer and hands ChatThrottleLib one chunk of a long message at a time (the next when the callback for the one before comes), in a queue per peer. So a peer who leaves has their unsent chunks dropped (the one already handed over still goes, and may draw "No player named …"), as has everyone when the link goes down. When a chunk fails, the rest of that message is dropped. A one-chunk message goes to ChatThrottleLib at once, at `ALERT`, whatever is waiting.
- **The result code:** ChatThrottleLib's callback gives the game's `Enum.SendAddonMessageResult` for each chunk, which AceComm reduced to true or false. The trace shows it on a failed chunk. Which one Forever gives for a whisper to a logged-out friend isn't known yet.

## Sync: recovering lost messages

A message is lost without anyone knowing: a lost chunk loses the whole DATA, and nothing tells the sender (`docs/research/addon-message-reliability.md`). The receiver knows only if another chunk of it arrived. There are no ACKs (ADR 0006). Instead DIGESTs go out on their own, and a friend who missed something sees it in one and asks:

- **Confirming DIGEST:** 20–30 s after own DATA goes out, a DIGEST follows it. A friend who missed the DATA sees a newer version and replies with their own DIGEST (to the sender only), which makes the sender owe it to them. A lost ding arrives within about 40 s.
- **Every minute:** while the link is up, a DIGEST goes out 55–65 s after the last one (any DIGEST to everyone restarts the wait, the confirming one included).
- **After a failed send or a lost message:** that friend gets a DIGEST of their own (`sendFailed`, above).
- **"Later" changes** (XP, gold, Play times, professions, catches) go out within 60 s instead of waiting for the heartbeat.
- **Taking turns:** a DIGEST holds 10 entries (one chunk): the own record, then any ids a reply DIGEST is meant to fetch (with the version held, 0 if none, so whoever holds them replies), then the other records in turn by id, carrying on from where the last DIGEST stopped. In a Crew of more than 10 Members every record is listed within `ceil((Members − 1) / 9)` DIGESTs. One that left records out says `partial = true`, and a record it doesn't list isn't owed. Older clients ignore the flag (and owe whatever is missing, as before), and a DIGEST without it means what it always did, so mixed versions sync with no protocol bump. Every DIGEST from this version also says `turns = true`; one without it comes from an older client. Since an older client answers every DIGEST that leaves records out with DATA for all of them, the every-minute DIGEST is skipped while one was heard in the last 15 minutes and there are more than 10 records (confirming and per-friend DIGESTs still go out). In an idle Crew of 14 with two older clients, that keeps the busiest Member at 27 whispers a minute instead of 105.
- **Replies go to the sender:** a DIGEST from a peer who is behind makes every peer holding a newer copy owe DATA to that peer only, and a DIGEST showing something newer is answered with a DIGEST to that peer only. What is owed, and when it is due (1–4 s later), is kept per peer, and dropped when that peer is `gone(name)`. A reply to someone else isn't seen, so it cancels nothing: a friend who is behind can get the same record from several peers, and nobody else is sent anything. Still to everyone: own DATA, the DIGEST on link up, the confirming DIGEST, the every-minute DIGEST, WHERE, DOING and leaving the Crew. A Member's own record heard as DATA from them most likely went to everyone (their reply to one peer looks the same, and is rare), so it is no longer owed to anyone; a later DIGEST catches the rare miss. No protocol bump: an older BFF keeps replying to everyone, and both directions still sync. If the link gives no sender, replies go to everyone and a reply heard cancels the same one owed, as before.
- **An own change that hasn't gone out yet** (a "later" change waiting for its send) isn't shown in a DIGEST, which lists the version everyone was last sent, and isn't owed to a peer who holds that version. Sent to one peer alone, they would hold a version the others lack and pass it on, reply after reply. If a peer lacks even the version that went out, own DATA goes out early (after the 1–4 s reply delay), to everyone.
- **In flight:** a record that went out to everyone (own DATA sent, or a Member's own record heard as DATA) in the last 2 s isn't owed to a DIGEST showing an older version: that DIGEST most likely crossed it on the way. A later DIGEST catches a real loss.
- **Traffic** (FakeNet, whispers sent a minute per Member, each chunk to each friend counted once; `BFF_TRAFFIC=1 busted tests/sync_spec.lua` prints them): a Crew of 4 idle, the busiest Member 4.2; one Member grinding, 6.0. A Crew of 6 idle, 7.0; grinding, 10.0 (before replies went to the sender only: 4.5, 11.4, 7.5 and 25.0). That is one whisper every 6 s, against the server's allowance of about one addon message a second per prefix (which whispers outside instances may not even count) and ChatThrottleLib's 800 B/s. DOINGs aren't in these figures (the sim's Members do nothing); at their fastest they add `others × 60 / max(15, 5 × others)` whispers a minute, 4 in a Crew of 2 and 12 from a Crew of 4 up.

## Loading pure code in game and in tests

Every file starts with `local _, ns = ...` and attaches itself to `ns`, the addon's private table. Files in `Core/` only touch `ns`, Lua builtins, the `bit` library (WoW and LuaJIT both have it) and the pure libraries (LibSerialize, LibDeflate). Files in `Link/` only touch `ns` and Lua builtins. The test loader mimics the `.toc` with `loadfile("Core/Ledger.lua")("BFF", ns)`, for every `Core/` and `Link/` file. A luacheck rule bans WoW globals in `Core/` and `Link/`.

## Tests

- **Runner:** busted under LuaJIT, linted with luacheck.
- **The interface is the test surface.** Tests create Cores and check `rows()`, the While you were away summary, Feed entries, and the recorded listener events and sent messages. They never look inside `db`, Ledger or Gossip.
- **Pure, stateless helper files may be tested directly**, table-style, as `codec_spec` does for Codec, `text_spec` for Text, `spare_rules_spec` for SpareRules, `commands_spec` for Commands, `professions_spec` for reading professions and `catches_spec` for reading the loot window, `deaths_spec` for which deaths count and counting each once. Anything with state or lifecycle in Core is tested through Core; the game-facing files below are tested through their own interfaces.
- **Fake network** (`Dev/FakeNet.lua`):
  - One shared virtual clock and scheduler, so every run plays out the same way.
  - Each simulated client is a real Core with a fake link and its own `db`.
  - Per client: online or offline (link up or down), lockdown (link down while still online), Pause, reload (a new Core over the same `db`), and crash (a new Core over a copy of `db` taken at the last logout or reload).
  - Delivery is a broadcast to every client whose link is up (or, with `to`, a whisper to one), after a small delay, with optional drops (`drop`: lost, no one told) and failed sends (`fail`: the sender hears `sendFailed`) to test the best-effort contract.
  Delivery includes the sender itself, as the real channel does. A client going offline fires `gone(name)` on the others; a crash can skip it.
  - With `FakeNet.new({ channels = true })` a client only hears clients in the same channel (its Crew's current channel generation), plus whispers from a client whose member list still has it (`sees(from, to)`, set by the test) when the receiver vouches for the sender with `fromKnownMember`, as the channel link does. A client whose Crew moves to another generation goes down and comes back up there.
  - Messages go through the real Codec, and travel as the chunks the real Framing splits them into: each client reassembles what it receives. `chunked(chunks, from, to)` says which chunks of a message reach a client and in what order, to lose or reorder single chunks; a message left incomplete is reported lost 30 s later and the receiver's Core hears `sendFailed`, as from the channel link.
- **Scenarios** include:
  - C logs in after missing A's ding, and learns it from B and D, who each send it to C only.
  - Bob's channel breaks and he moves to the next generation while Ann's still works: Ann still sees Bob and whispers him, Bob vouches for her, and his record carries the generation to Ann, who moves too.
  - A DIGEST showing something newer is answered with a DIGEST to its sender only; with no sender, the replies go to everyone.
  - Own DATA and the DIGESTs on link up, after own DATA and every minute still go to everyone.
  - A friend who logs out before a reply to them was due is sent nothing.
  - An own change that can wait isn't shown in a DIGEST or sent to one friend; it goes to everyone when due, or early if a friend lacks what went out before it.
  - A crashes and its next version still wins.
  - Changes made during lockdown go out after one DIGEST when it clears.
  - A lost message is recovered at the next `up()`, and a lost ding within a minute while it stays up.
  - A failed send to one friend leaves the link up for the others and sends that friend a DIGEST of their own.
  - A message whose chunks arrive in another order is delivered; one with a chunk lost isn't, and the friend who missed it asks again.
  - XP and gold reach friends within a minute.
  - In a Crew of 14, every record is listed in a DIGEST within two rounds, and records left out make no one send DATA.
  - A Member on an older BFF (`tests/fixtures/legacy_gossip.lua`) syncs both ways, in a Crew of 3 and of 13.
  - Traffic stays well under the throttle in a Crew of 4 and of 6.
  - A removed Member is never shown or relayed.
  - Someone going quiet flips to offline after 12 minutes once out of the channel; while still in it (lockdown) they stay online but quiet, go offline on a leave or a bounced whisper, and show plain online when heard again.
  - A Paused Member leaves the channel, shows offline at once, catches up on resume, and can still leave the Crew.
  - Ten Members with three Characters each: the DIGEST fits one message.
- **Framing** (`framing_spec`): splitting, reassembling in any order and interleaved, the 30 s loss report and what a chunk starts with, through Framing's own interface with a clock the spec moves.
- **Presence** (`presence_spec`): the rules above, through Presence's own interface with a clock the spec moves: no WoW stand-ins. `channel_link_spec` checks the wiring: a silent peer gets no whispers and Core hears no `gone`, a peer dropped as not found stays out when the list names them, a stranger's whisper is held, and the link comes up without a member list.
- **WoW stand-ins** (`tests/wow_stubs.lua`): for the game-facing files tested offline: the channel link (`channel_link_spec`: targeted sends, priorities, a chunk at a time, unsent chunks dropped when a peer leaves, chunks received in any order, a protocol 1 message still read, a lost message asking that peer again, failed sends, "Player is offline.", "No player named …" after a peer left with whispers queued, its trace lines and `state()`, with a stand-in secret value that errors if read), the sync log (`sync_log_spec`: the cap, saving and restoring) and the Report's text (`report_spec`). Their records are kept and relayed like real ones, so it only runs in a Crew where no one else is known yet. `/bff sim ding` makes one ding, `/bff sim stop` logs them out. The `.toc` lists `Dev/` inside `#@do-not-package@`, so releases don't load it. Echo mode on the channel link loops your own messages back to you.

## The panel and its tabs

`UI/Panel.lua` is a host. It owns the window (size, place, resize grip), the header, the Camp band and its firelight, the sidebar and the setup screen shown before you're in a Crew. Above the setup sits the no-Crew card, which shows the lines from Core's `elsewhere()`: where your Crew is on other Rulesets, the question about a Crew from before Rulesets that BFF can't place (It's here / Start fresh), and Bring your Crew here for the other faction's provisional Crew. Everything inside the content area belongs to a tab.

The panel keeps **one list of tabs**, `TABS`: each with its key (what `Panel.show(key)` and `/bff` commands open), its sidebar label and place, its module, for Feed and Spares the badge count, and for Settings `withoutCrew` (it opens before you're in a Crew; every other tab shows the setup screen then). The sidebar, switching and leaving all read that list. The `.toc` loads every tab before `Panel.lua`.

**The tab seam.** A tab module has:

- `draw(page)`, required. Called on every redraw while the tab is open: when it's picked, on a Core change, every 30 s and when a resize or move ends (the `panelPlace` setting).
- `leave(closed)`, optional. Called when the tab stops being shown: another tab was picked (`closed` false), or the panel was hidden (`closed` true). Hiding the panel and then reopening it on another tab calls it twice, so it must be safe to repeat.

`page` is what the panel gives the tab, one per tab and kept between draws:

- `page.frame`: the tab's own frame, filling the content area. The panel shows it while the tab is open and hides it otherwise, so a tab never hides itself.
- `page:scrollView()`: the panel's scroll view on that frame, made on the first call and the same one after. It fills the frame, less the scrollbar's gutter on the right (`ScrollView.GUTTER`); a tab with fixed parts above or below (Roster's footer, Professions' header row, Catches' summary and recent catches) leaves room for them with `view:Between(top, bottom)`. It has a `content` frame to draw into and `view:Fit(height)`, which sets the content's height and places the thumb. `UI/ScrollView.lua` makes it.
- `page.width` and `page.height`: the content area's size; `page.listWidth`: the width inside the scroll view.
- `page.redraw()`: asks for a redraw of the whole panel (a menu pick, a row expanded).
- `page.core`: Core. Tabs talk only to Core's interface and the game adapters (`ns.Actions`, `ns.Bags`), never to the pure feature modules.
- `page.window`: the panel's window, for placing a tooltip beside it.
- `page.campShown`: whether the Camp band is shown. Roster rows show Camp figures or class icons by it, and the Dungeons tab its heads or dots.

**Each tab owns its visit.** Feed's `draw` calls `core:openFeed()` before reading `feed()`, and its `leave` calls `core:leaveFeed()`. Trophies and What's new do the same with `openTrophies`/`leaveTrophies` and `openWhatsNew`/`leaveWhatsNew`. Spares marks Spares seen as it draws them. Trophies keeps its cabinet open when the panel is only hidden.

**Links passed in on purpose.** Two tabs depend on another's state, and get it handed to them rather than shared: the Professions grid sorts by the Roster's order (`Panel.start` calls `ProfessionsTab.sortLike(RosterTab.order)`), and Roster rows read `page.campShown`. Other tabs open a tab through `Panel.show`, and the Roster's "When does X play?" through `Panel.showPlayTimes(memberId)`, which picks the Member with `PlayTimesTab.pick`.
