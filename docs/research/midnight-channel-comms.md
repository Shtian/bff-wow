# Can addons talk over a hidden custom channel under Midnight?

Research for [issue #2](https://github.com/Shtian/bff-wow/issues/2). Researched 2026-10-31 against the Retail 12.1.5 and Forever 1.60.1 clients.

## Answer

**Yes, outside chat lockdown.** An addon can join a custom channel from a timer, with no click or key press. It can remove the channel from its chat frames and use `C_ChatInfo.SendAddonMessage(prefix, msg, "CHANNEL", channelIndex)` to send and receive. The big addons Total RP 3 and Musician do exactly this today on Retail. Total RP 3 also turns it on for WoW: Forever by name.

Midnight adds one restriction that matters to BFF, **chat messaging lockdown**. It applies during an instance encounter, an active Mythic+ run or a live PvP match. While it is active, addons can't send messages (`Enum.SendAddonMessageResult.AddOnMessageLockdown`) and can't use the chat channel APIs. Normal open-world combat does **not** trigger it. BFF syncs slow-moving social data, so a send queue that waits for lockdown to end handles this fully.

**Confidence: high** that the mechanism works in the open world on Forever. **Medium** on the exact lockdown behaviour, because Blizzard's notes describe it but no API doc lists every affected call. **Medium** on throttle numbers, because the server can change them at any time.

Labels used below: **[Confirmed]** means a primary source states it. **[Inference]** means it is reasoned from primary sources or from shipping addon code, not stated outright.

## 1. Joining a channel without a hardware event

- **[Confirmed]** `JoinChannelByName(name [, password, frameID, hasVoice])` and `JoinTemporaryChannel(...)` are plain global functions. The temporary variant leaves the channel on logout. Their wiki pages list no protected or hardware-event requirement. ([API JoinChannelByName](https://warcraft.wiki.gg/wiki/API_JoinChannelByName), [API JoinTemporaryChannel](https://warcraft.wiki.gg/wiki/API_JoinTemporaryChannel))
- **[Confirmed by shipping code]** Total RP 3 (`main`, 2026-10-24) calls `JoinChannelByName` from a `C_Timer.NewTicker` callback, so no hardware event is involved. It enables this when `WOW_PROJECT_ID == WOW_PROJECT_MAINLINE or WOW_PROJECT_ID == WOW_PROJECT_CAMELOT`, and `WOW_PROJECT_CAMELOT` (18) is WoW: Forever. ([CommunicationProtocolBroadcast.lua L419-L425](https://github.com/Total-RP/Total-RP-3/blob/e613c8acb674802d1bcaf76dcc6be1132fa5eb12/totalRP3/Core/CommunicationProtocolBroadcast.lua#L419-L425), [Globals.lua L77-L78](https://github.com/Total-RP/Total-RP-3/blob/e613c8acb674802d1bcaf76dcc6be1132fa5eb12/totalRP3/Core/Globals.lua#L77-L78), [WOW_PROJECT_ID](https://warcraft.wiki.gg/wiki/WOW_PROJECT_ID))
- **[Confirmed by shipping code]** Musician calls `JoinTemporaryChannel(channel, password)` from a 1-second `C_Timer` ticker. Before joining it checks `C_ChatInfo.InChatMessagingLockdown()` and waits if lockdown is active. ([Musician.Comm.lua L309-L384, L123-L130](https://github.com/LenweSaralonde/Musician/blob/cdb8e40e9800ea5a19afd8768169389a05cc81f9/core/Musician.Comm.lua#L309-L384))
- **[Confirmed]** 12.0.5 changed this: "Various chat channel APIs are no longer usable while chat lockdown is in effect, or from within macros." (Blizzard, 2026-04-10, quoted in [Patch 12.0.5/API changes/notes](https://warcraft.wiki.gg/wiki/Patch_12.0.5/API_changes/notes)). Blizzard does not list which APIs are affected. **[Inference]** Treat join and leave as unavailable during lockdown.
- **[Confirmed, historical]** The hardware-event rule added in 8.2.5 covers `SendChatMessage` to SAY, YELL and CHANNEL, meaning visible chat text. It does not cover joining channels or addon messages. ([wowinterface thread](https://wowinterface.com/forums/archive/index.php/t-58641.html), secondary)
- **[Inference]** The server enforces a per-character cap on custom channels. Total RP 3 treats `ERR_TOO_MANY_CHAT_CHANNELS` as "already in 10 channels" ([L466-L470](https://github.com/Total-RP/Total-RP-3/blob/e613c8acb674802d1bcaf76dcc6be1132fa5eb12/totalRP3/Core/CommunicationProtocolBroadcast.lua#L466-L470)). The UI constant `MaxChatChannels` is 20, but that counts every channel slot, not custom channels. BFF needs a clear error for this case.
- **[Inference]** Join right after login and the result is racy. Both addons wait until the channel list has no gaps (General, Trade and so on are in place), with a 10-second fallback, so the custom channel doesn't take slot /1 or /2. BFF should copy this.

## 2. Hiding the channel from chat frames

- **[Confirmed]** Blizzard's own `ChatFrameMixin:RemoveChannel(channel)` clears the frame's `channelList` and `zoneChannelList` entries and calls `RemoveChatWindowChannel(frameID, channel)`. ([ChatFrame.lua L178-L188](https://github.com/Gethe/wow-ui-source/blob/ca8368f2f2380cbe696854f7f2646387c278a61b/Interface/AddOns/Blizzard_ChatFrameBase/Shared/ChatFrame.lua#L178-L188))
- **[Confirmed by shipping code]** Total RP 3 does the same in `hideBroadcastChannelFromChatFrame` ([L298-L314](https://github.com/Total-RP/Total-RP-3/blob/e613c8acb674802d1bcaf76dcc6be1132fa5eb12/totalRP3/Core/CommunicationProtocolBroadcast.lua#L298-L314)). Addon messages never show in chat frames anyway. Hiding only stops stray plain-text messages and join/leave notices.
- **[Confirmed by shipping code]** Total RP 3 turned off its channel reordering (`C_ChatInfo.SwapChatChannelsByChannelIndex`) because "Swapping channels currently taints leading to nasty errors during secret chat situations." ([L321-L324](https://github.com/Total-RP/Total-RP-3/blob/e613c8acb674802d1bcaf76dcc6be1132fa5eb12/totalRP3/Core/CommunicationProtocolBroadcast.lua#L321-L324)) BFF should not reorder channels.
- **[Inference]** "Hidden" only means hidden from chat windows. The channel still shows in the Channels UI and `/chatlist`, and anyone who learns the name can join it. A channel name and password both derived from the Crew code keep strangers out. Messages should still be checked against the known Member list.

## 3. SendAddonMessage over CHANNEL

- **[Confirmed]** Signature: `result = C_ChatInfo.SendAddonMessage(prefix, message [, chatType [, target]])`. `"CHANNEL"` works on Retail but not Classic, and `target` is the channel **number** (from `GetChannelName(name)`). It is marked `SecretArguments = "NotAllowed"`. ([wiki](https://warcraft.wiki.gg/wiki/API_C_ChatInfo.SendAddonMessage), [ChatInfoDocumentation.lua L516-L533 (forever branch)](https://github.com/Gethe/wow-ui-source/blob/ca8368f2f2380cbe696854f7f2646387c278a61b/Interface/AddOns/Blizzard_APIDocumentationGenerated/ChatInfoDocumentation.lua#L516-L533))
- **[Confirmed]** Recipients must call `C_ChatInfo.RegisterAddonMessagePrefix(prefix)` and then receive `CHAT_MSG_ADDON` (prefix, text, channel, sender, target, zoneChannelID, localID, name, instanceID). Unlike most `CHAT_MSG_*` events, `CHAT_MSG_ADDON` is **not** marked `SecretInChatMessagingLockdown` in the generated docs. ([ChatInfoDocumentation.lua L800-L817](https://github.com/Gethe/wow-ui-source/blob/ca8368f2f2380cbe696854f7f2646387c278a61b/Interface/AddOns/Blizzard_APIDocumentationGenerated/ChatInfoDocumentation.lua#L800-L817))
- **[Confirmed]** The Forever API docs match Retail 12.1.5 for `C_ChatInfo`, apart from one extra event (`CHAT_MSG_COLLECTED_APPEARANCE`). (Diff of `ChatInfoDocumentation.lua`, `live` vs `forever` branches of [Gethe/wow-ui-source](https://github.com/Gethe/wow-ui-source))
- **[Confirmed]** Forever (and Retail from 12.1.7) **blocks trial and Veteran accounts from sending addon messages**. ([wiki Details](https://warcraft.wiki.gg/wiki/API_C_ChatInfo.SendAddonMessage)) A Member on such an account can receive messages but can't publish.
- **[Confirmed]** 12.0.0 added `Enum.SendAddonMessageResult.AddOnMessageLockdown` (11) and `TargetOffline` (12). ([Patch 12.0.0/API changes](https://warcraft.wiki.gg/wiki/Patch_12.0.0/API_changes), [Enum.SendAddonMessageResult](https://warcraft.wiki.gg/wiki/Enum.SendAddonMessageResult))

## 4. Restrictions in combat, instances and encounters (Midnight)

- **[Confirmed]** In the first alpha, communication in instances was blocked outright: "While in an instance, chat messages will be sent to Lua as Secret Values, and addons are not allowed to send communications to other players (either through addon comms or regular chat)." (Blizzard, 2025-10-01)
- **[Confirmed]** Blizzard narrowed this in Alpha 3: "The ability to send addon messages and read chat is currently restricted entirely while inside an instance. This has been relaxed to only apply when any of the following are true: A mythic keystone run has started and not yet completed. A PvP match has started and not yet completed. An instance encounter is in progress." (Blizzard, 2025-10-11) Both quotes come from [Patch 12.0.0/API changes/notes](https://warcraft.wiki.gg/wiki/Patch_12.0.0/API_changes/notes), the WoWUIDev Discord posts archived verbatim.
- **[Confirmed]** The client has a separate restriction type for this: `Enum.AddOnRestrictionType.Chat` (5), "The player is in a state where addon chat communications are restricted". It is separate from `Combat` (0), `Encounter` (1), `ChallengeMode` (2), `PvPMatch` (3) and `Map` (4). You can query it with `C_ChatInfo.InChatMessagingLockdown()`, `C_RestrictedActions.IsAddOnRestrictionActive(type)` and the `ADDON_RESTRICTION_STATE_CHANGED` event. ([RestrictedActionsConstantsDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/ca8368f2f2380cbe696854f7f2646387c278a61b/Interface/AddOns/Blizzard_APIDocumentationGenerated/RestrictedActionsConstantsDocumentation.lua), [RestrictedActionsDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/ca8368f2f2380cbe696854f7f2646387c278a61b/Interface/AddOns/Blizzard_APIDocumentationGenerated/RestrictedActionsDocumentation.lua))
- **[Confirmed]** Normal combat is not chat lockdown. In 12.0.5 Blizzard "loosened [countdown, ready check, ping and loot method restrictions] to only apply when in chat messaging lockdown rather than in all combat." ([12.0.5 notes](https://warcraft.wiki.gg/wiki/Patch_12.0.5/API_changes/notes))
- **[Confirmed]** Blizzard keeps closing side channels during lockdown: AFK/DND flags, LFG listings, calendar, club notes and voice member lists all go secret. ([12.0.0 notes](https://warcraft.wiki.gg/wiki/Patch_12.0.0/API_changes/notes), around "addressed a whole host of addon communication workarounds") **[Inference]** Don't rely on any trick to signal during lockdown. Just wait it out.
- **[Inference]** It is unconfirmed whether `CHAT_MSG_ADDON` fires for *incoming* messages while the receiver is in lockdown. The sender can't send during its own lockdown. If the receiver is in lockdown and the sender isn't, the message may or may not arrive. BFF must not assume delivery: use anti-entropy (version vectors or digests) on the next sync, not fire-and-forget.
- **[Confirmed]** For testing, the `addonChatRestrictionsForced` CVar forces the client into chat lockdown. It does not persist across restarts. ([12.0.0 notes](https://warcraft.wiki.gg/wiki/Patch_12.0.0/API_changes/notes))
- **[Confirmed]** `C_ChatInfo.AreOutgoingAddonChatMessagesRestricted()` is "controlled on a realm-by-realm basis (tournament realms allow it)". Blizzard's own UI checks it before loading the cooldown broadcaster. ([ChatInfoDocumentation.lua L11-L19](https://github.com/Gethe/wow-ui-source/blob/ca8368f2f2380cbe696854f7f2646387c278a61b/Interface/AddOns/Blizzard_APIDocumentationGenerated/ChatInfoDocumentation.lua#L11-L19)) **[Inference]** BFF should check it once at load and report it if true.

## 5. Size and rate limits

- **[Confirmed]** The prefix can be at most 16 characters. The message can be at most 255 characters, and any byte 1-255 is allowed (no NUL). ([wiki](https://warcraft.wiki.gg/wiki/API_C_ChatInfo.SendAddonMessage))
- **[Confirmed]** Since 10.2.7 every chat type has a per-prefix throttle: a burst of 10 messages, refilling at 1 message per second. Going over returns `AddonMessageThrottle`. "This restriction does not apply to whispers outside of instanced content." "All numbers provided above are the default values, however these can be dynamically reconfigured by the server at any time." Sending heavily on several prefixes at once "may" disconnect the client. ([wiki, Message throttling](https://warcraft.wiki.gg/wiki/API_C_ChatInfo.SendAddonMessage))
- **[Confirmed]** `CHANNEL` also has its own server result, `ChannelThrottle` (8). Its numbers are not published. ([Enum.SendAddonMessageResult](https://warcraft.wiki.gg/wiki/Enum.SendAddonMessageResult))
- **[Confirmed]** Ace3 r1377 (2025-10-28) updated ChatThrottleLib for 12.0, and r1403 (2026-08-12) "Fixed errors from secrets during chat lockdown". ChatThrottleLib's bandwidth defaults are `MAX_CPS = 800` and `BURST = 4000` bytes. ([Ace3 changelog.txt](https://github.com/WoWUIDev/Ace3/blob/ac3d1225037e0dc74e025a72342c0f7824aae147/changelog.txt), [ChatThrottleLib.lua L60-L63](https://github.com/WoWUIDev/Ace3/blob/ac3d1225037e0dc74e025a72342c0f7824aae147/AceComm-3.0/ChatThrottleLib.lua#L60-L63))
- **[Inference]** For a Crew of 10 or fewer, one prefix at about 1 message per second over the channel is plenty for presence, Feed entries and digests. Send through AceComm or ChatThrottleLib (or a small queue of our own that respects the result codes), and split payloads over about 240 bytes.

## 6. Best same-realm fallback if the channel is blocked

In order of preference:

1. **Whisper mesh (`"WHISPER"`)** **[Confirmed]** Works with any player on the same or a connected realm. It is exempt from the per-prefix throttle outside instances, and from 12.0.0 it returns `TargetOffline` (12), a cheap presence probe. ([wiki](https://warcraft.wiki.gg/wiki/API_C_ChatInfo.SendAddonMessage), [Enum](https://warcraft.wiki.gg/wiki/Enum.SendAddonMessageResult)) **[Inference]** With 10 or fewer Members a full mesh is at most 9 sends per broadcast, which is cheap. It needs the Member roster, meaning the Characters' names, which BFF already stores. This makes a good primary or secondary path, not just a fallback.
2. **`GUILD`**, if the whole Crew shares a guild. **[Confirmed]** It is a supported chat type.
3. **Battle.net game data** (`C_BattleNet.SendGameData(gameAccountID, prefix, data)` → `BN_CHAT_MSG_ADDON`). **[Confirmed]** It exists and returns `SendAddonMessageResult`. ([BattleNetDocumentation.lua L255-L269](https://github.com/Gethe/wow-ui-source/blob/ca8368f2f2380cbe696854f7f2646387c278a61b/Interface/AddOns/Blizzard_APIDocumentationGenerated/BattleNetDocumentation.lua#L255-L269)) **[Inference]** It only reaches Battle.net friends who are online in WoW, but it ignores realm and faction. Worth keeping in mind for later.
4. **A one-time "Join" button** is **not needed**. Joining needs no hardware event (section 1). A button would only help if Blizzard later protects `JoinChannelByName`.

## Implications for BFF (recommendation, inference)

- Run two transports behind one seam: the custom channel (one send reaches every online Member) and a whisper mesh (rescue and point-to-point). Both are queued.
- Gate every send on `C_ChatInfo.InChatMessagingLockdown()`. Listen for `ADDON_RESTRICTION_STATE_CHANGED` with `Enum.AddOnRestrictionType.Chat` and flush the queue when it clears. Handle `AddOnMessageLockdown`, `AddonMessageThrottle` and `ChannelThrottle` results by re-queueing.
- Join after the channel list settles, never during lockdown. Don't reorder channels. Remove the channel from every chat frame. Use a password derived from the Crew code.
- Make sync idempotent and catch-up based, so messages lost to lockdown or a missed join heal on the next exchange.
- Show a clear status when the local account is trial or Veteran (can't send) or when `AreOutgoingAddonChatMessagesRestricted()` is true.
- Still to check in game on Forever: (a) whether `CHAT_MSG_ADDON` fires for a receiver in lockdown, (b) the exact `ChannelThrottle` rate, (c) whether custom channels span connected realms.
